# Security and operations specification

This is the target for the private app. The foundation release implements the web and household access, session, CSRF/origin, trusted-proxy and request-validation controls below, with the checks listed in [development](development.md). Document handling is implemented as described under Documents below, and the optional MCP listener and in-app proposal review as described under Optional LAN-only MCP. Automated backups remain planned; the operator procedures for deployment, upgrade, encrypted backup and restore are in [operations](operations.md).

## Implemented foundation controls

- **First-run setup.** While no administrator exists, `/setup` (and `POST /api/setup`) creates the household and first administrator for whoever presents the setup token. The token is `TALLYMED_SETUP_TOKEN` (32 to 128 printable characters with at least 16 distinct ones, no sequential or keyboard runs, repeated blocks, common words or placeholders; `openssl rand -base64 32` passes; an invalid value never stops the app: once an administrator exists it is ignored, and while setup is needed setup stays closed and the log names the problem) or, if empty, 256 random bits generated at startup and printed once to the console. It is compared in constant time (both sides hashed first), never stored in the database, audit rows or structured logs (a generated token exists only in process memory and in the one console banner), and the banner for a configured token names the variable only. The attempt limit is checked, the token compared and a failure recorded in one synchronous step (no await in between), so a concurrent burst cannot exceed it: ten failures per 15 minutes overall and five per trusted client address, refusing even the right token while spent; the counters are in memory and a restart resets them. This also means someone who can reach the setup page can keep setup locked for the operator by spending the budget every 15 minutes (availability only, never a bypass); the operator's recovery is to restart the web process (a generated token is replaced by a new printed one), ideally while the page is reachable only privately. Input errors with the right token neither spend attempts nor the token. Once the first administrator exists, the page and endpoint answer 404 for everyone and the token is dropped; two simultaneous valid setups produce exactly one household (advisory lock, then the primary key on `bootstrap_state`; the loser gets `bootstrap_closed`). The audit row `bootstrap.completed` records only the method and token source. Same-origin and body-size rules apply as for sign-in. Operators who hold the database credentials can already do anything, so no local bootstrap command is kept.
- **Accounts.** Administrators create one-time invitation links (SHA-256 digest stored, 72 hours, single use) for operators or administrators. Roles map to capabilities in `server/authz.ts`; every service call authorizes and scopes by household. The last active administrator cannot be demoted or disabled.
- **Passwords.** Argon2id (`@node-rs/argon2` defaults), 12 to 128 characters. Unknown accounts take comparable time and return the same generic error.
- **Password change and administrator reset.** Any signed-in account can change its own password on `/account/password` (the current password is required and wrong guesses are throttled five per 15 minutes per account, even with a valid session). An administrator can reset another active account (never their own) from the Operators page: the server generates a random temporary password (about 99 bits, `K7M2P-9QXWD-...`), stores only its Argon2id hash in place of the old hash, shows it to the administrator once on a never-cached page, and never writes it to the database in the clear, to a log or to the audit trail. The reset signs the account out everywhere, clears its sign-in lockout and supersedes any earlier temporary password. The temporary password works for one sign-in and expires after `TALLYMED_TEMP_PASSWORD_SECONDS` (default 4 hours); that sign-in yields a restricted session of at most `TALLYMED_PASSWORD_CHANGE_SESSION_SECONDS` (default 15 minutes). While `users.must_change_password` is set, every authenticated route and page is closed except choosing a new password and signing out (`password_change_required`): the check is in the shared POST pipeline (`route()`, closed by default, so a new route cannot forget it) and in the page and GET helpers, and `tests/web/password-reset.test.mjs` fails if an API route is added without being classified. Changing a password revokes every session of the account and issues a fresh one for the device that changed it. The reset runs under the household administrator lock and re-checks the actor's session and role inside it, so two administrators cannot reset each other at once; the account being reset must be active and the household must keep another administrator with a usable password. A reset also needs the target's row version, so a double submit issues one secret. Audit events: `auth.password_reset_issued`, `auth.temporary_password_used`, `auth.password_changed` and bounded `auth.password_change_failed` / `auth.password_change_locked`, with no secret in any detail. Accepted limitation: someone who watches the administrator's screen or hears the temporary password can use it first (it works once, and then the real person's attempt fails visibly and is audited); hand it over in person or by phone, never in a shared chat.
- **Sessions.** 256-bit random tokens in a `__Host-` `Secure` `HttpOnly` `SameSite=Lax` cookie (plain name without `Secure` only for a loopback `http` origin). Only a SHA-256 digest is stored. Sessions expire after 12 hours absolute or 2 hours idle, are revoked at logout, at role or status changes and when login rotates a presented session. A client can never choose a session identifier.
- **Throttling.** Five failures in 15 minutes lock an account; 20 failures lock a trusted client address. Addresses count only when the trusted proxy supplied them. Each attempt is recorded as a failure under per-account and per-address advisory locks before the password is verified, so concurrent bursts cannot exceed the limits. A successful sign-in clears the account counter. Expired attempt rows are pruned on sign-in. Failed-sign-in audit rows are limited to the first failure and the lockout per window and only for existing accounts. An open invitation can be revoked by an administrator (audited) and then re-issued.
- **CSRF.** Every POST requires the canonical `Origin` (or `Referer`) and no cross-site `Sec-Fetch-Site`; authenticated POSTs also need a per-session HMAC token (`x-csrf-token` header or `csrf` form field).
- **Validation.** Bodies are at most 8 KiB, JSON or urlencoded only, parsed with strict schemas that reject unknown or duplicate fields. Errors use stable codes (`invalid_input`, `unauthenticated`, `forbidden`, `csrf_failed`, `not_found`, `stale_version`, `conflict`, `rate_limited`, ...). Logs pass through a redactor and never include bodies, cookies or driver messages.
- **Audit.** Bootstrap, sign-in and sign-out, failed sign-in, invitations, password resets and changes, and account changes are written in the same transaction as the change. `audit_events` rejects update, delete and truncate.

## Reverse proxy contract

Set `TALLYMED_CANONICAL_ORIGIN` to the public `https://` origin. The app never derives its origin, redirects or cookie attributes from `Host` or `X-Forwarded-Host`. Set `TALLYMED_PROXY_SECRET` (32 or more random characters) and configure the proxy to (1) delete any client-supplied `X-Forwarded-*`, `Forwarded`, `X-Real-IP` and `X-Tallymed-Proxy-Secret` headers, then (2) send `X-Tallymed-Proxy-Secret: <secret>`, `X-Forwarded-For: <client address>` (append only the address the proxy observed) and `X-Forwarded-Proto: https`. The app uses forwarded values only when the secret matches, uses the right-most address and refuses a trusted request that reports `http` for an `https` origin. Publish the upstream only on a private interface or Compose network. Never route an MCP path through this proxy.

Example nginx location (adapt and test; `$remote_addr` is the only address the proxy vouches for):

```nginx
location / {
  proxy_pass http://tallymed-web:3000;
  proxy_set_header Host $host;
  proxy_set_header X-Forwarded-For $remote_addr;
  proxy_set_header X-Forwarded-Proto $scheme;
  proxy_set_header X-Real-IP "";
  proxy_set_header Forwarded "";
  proxy_set_header X-Tallymed-Proxy-Secret "<secret from your secret store>";
}
```

## Web and household access

Create the first administrator through a one-time setup token (operator-defined or generated and printed to the console once). Close setup permanently after account creation. Use invite/provisioning for additional authorized operators. Define administrative and operator capabilities and validate access at every action, route, lookup, export and download. Hash passwords with a maintained password-hashing library. Use revocable sessions, rotation at login and privilege changes, expiry, logout and login throttling. Use secure, HTTP-only, same-site cookies on HTTPS, and CSRF/origin validation for state changes. Enforce household and actor scope independently of UI controls. Validate inputs and bound body sizes, query sizes and rate limits. Redact financial and medical content, auth headers, cookies and secrets from logs and errors.

## Reverse proxy and service exposure

Deploy the web UI at a dedicated origin such as `https://tallymed.example` behind an operator-managed TLS reverse proxy. Use a configured canonical origin for redirects, secure cookies and origin validation. The proxy sets trusted forwarded headers and strips client-supplied values. App code trusts them only from the configured proxy path. Bind the upstream privately or use a shared private container network. Set upload limits and timeouts for document requests. Keep PostgreSQL and storage private. The public GitHub Pages deployment serves marketing only. The web reverse proxy never forwards to MCP. Validate HTTPS sign-in, redirects, origin checks, large permitted uploads and downloads through the real proxy before release.

## Documents and proposals

Allowlist supported formats and verify content signatures and size. Use opaque storage keys, private permissions, quarantine/validation, authorized streaming and safe download headers. Treat filenames, OCR, documents, provider notes and AI output as untrusted. Never execute embedded content. Recover safely from upload/storage failures using explicit document states, and clean up abandoned objects. Audit sensitive actions with minimal payloads.

Implemented controls (M05):

- **Formats.** PDF, PNG and JPEG only. The type comes from the bytes: PNG chunks are walked and checksummed and must end at IEND, JPEG markers are walked and must end at the end-of-image marker (up to 64 KB of zero padding after it is allowed), and a PDF must start with its header at byte zero, end with an EOF marker, carry no ZIP end record and show no script, launch, embedded-file, rich-media, form-submission or encryption names (name escapes decoded). The declared type and the extension must agree with the content or the upload is refused, and the recorded media type is the sniffed one. The PDF scan is best-effort, not a guarantee: one linear pass tokenizes the file as a reader would (comments, strings, names, dictionaries, `stream` bodies by a verified `/Length` or the first `endstream`), so a name counts only where it is a name, fake stream markers in comments or strings mean nothing, and names inside binary stream data are never looked at. Every object stream (`/Type /ObjStm`) is inflated (bounded) and tokenized the same way. Anything the pass cannot parse unambiguously refuses the file (a repeated dictionary key, a `/Length` that disagrees with the first `endstream`, an object stream without a direct `/Length`, `/OpenAction` with anything but a destination array, unbalanced delimiters, an unterminated string, a stream without a dictionary or without `endstream`, an object stream with a filter chain, another filter, a predictor or corrupt data, expansion over 16 MB, more than 4096 object streams). Work is bounded by the file size and the inflate budget. A reader may still parse a crafted file differently from this scan, so the other controls below do not depend on it and a saved PDF should be treated as untrusted in a local reader. Images are bounded to 50 megapixels.
- **Size.** 10 MB per file by default (`TALLYMED_DOCUMENT_MAX_MB`, 1 to 25) and 2 GB per household (`TALLYMED_DOCUMENT_QUOTA_MB`), enforced under a per-household lock. The multipart body is bounded by declared length and again as it is read, and the request is authenticated before the body is read. Set the proxy's body limit to the same value plus a small margin.
- **Names and keys.** File names are display-only (path parts, control and bidirectional characters stripped, restricted character set, forced extension) and never reach a path. Objects live under a server-generated 128-bit key, validated on every store call, written with `O_EXCL | O_NOFOLLOW` and mode 0600 in 0700 directories. The volume (`TALLYMED_DOCUMENTS_DIR`) must be an absolute path outside the web root and is refused if it contains a `public` or `.next` segment.
- **Workflow.** Validate, write to quarantine, read back and compare the checksum, promote into the object area, then record the rows in one transaction; any failure removes the object. A crash between promote and commit leaves an unreferenced object that `cleanup --apply` removes after a 24-hour grace period counted from promotion, so a row never points at bytes that were not stored and verified.
- **Download.** Authenticated, household scoped (another household's ID is a 404), the stored size and SHA-256 are verified before sending and mismatched bytes are never served. Responses carry the recorded `Content-Type`, `X-Content-Type-Options: nosniff`, `Content-Disposition: attachment` (inline only for PNG and JPEG on request, never PDF), `Content-Security-Policy: default-src 'none'; sandbox`, `Cross-Origin-Resource-Policy: same-origin` and `Cache-Control: private, no-store`. Document IDs are the only identifiers in URLs; no file name, title or checksum appears in a URL or a log line.
- **Mutations.** Upload, version, attach, detach, update and remove are POST-only with the canonical origin check, the CSRF token and a session. Every one is audited with before and after counts or checksums; titles, notes, reasons and file names are not copied into audit detail. Downloads are audited with the document and version only.
- **Removal.** A document with an active link cannot be removed (service check and a commit-time database guard). Removal is a tombstone; bytes are purged by `cleanup` after `TALLYMED_DOCUMENT_RETENTION_DAYS` (30 by default) and the row, checksum and link history stay (a detached link to a removed document is still shown in the record's history). Until the purge a removed document can be restored by an operator in one maintenance transaction: `begin; alter table documents disable trigger documents_guard_change; update documents set removed_at = null, removed_by = null, removal_reason = null where id = '<document id>'; set constraints all immediate; alter table documents enable trigger documents_guard_change; commit;`.

Operator commands (`npm run documents -w @tallymed/web -- verify|cleanup`, or `node apps/web/cli/documents.ts` in the image): `verify` compares every stored version with its recorded size and checksum, and lists missing, changed and unreferenced files by document and version number (exit 1 on a missing or changed file). `cleanup` is a dry run that prints what it would do; `cleanup --apply` removes quarantined files and unreferenced objects older than 24 hours and purges expired bytes, and refuses to apply when the database does not appear to match the volume (most old files unreferenced, or no versions at all) unless `--force`. Run `verify` after every restore and before trusting a backup, read its `unreferenced` list before applying `cleanup`, and schedule `cleanup --apply` daily. At most four uploads run at once per process (a 429 `busy` otherwise).

## Optional LAN-only MCP

Run MCP as a separate opt-in process on a private interface with a host firewall allowlist. Require both a network restriction and per-client authentication. Use HTTPS within the LAN, validate Origin when applicable, and use scoped, expiring and revocable client credentials. Store no plaintext credentials in the database or logs. Bind localhost for same-host use. Use a maintained MCP SDK and choose client-compatible auth and transport against the current MCP spec during implementation. The service exposes narrowly scoped reads and proposal creation. It has no direct tool to approve proposals, modify posted money, mutate accounts, or bypass browser authorization. Limit returned data and metadata, tool scopes and response size. Record tool calls and outcomes with redaction.

Human approval in the authenticated UI must recheck current document and target versions and authorization. Apply each proposal atomically and once, and record its provenance and rejection/approval. Treat AI instructions in uploaded content as data. Network-local MCP access can still lead a client to send selected data to a cloud provider. Use explicit opt-in and document the client/provider data boundary. Claude development threads use synthetic fixtures and have no connection to a live TallyMed install.

Implemented controls (M06; setup, client configuration and the data boundary are in [mcp](mcp.md)):

- **Off by default.** The listener is a separate command (`apps/web/cli/mcp.ts`, image `infra/Dockerfile.mcp`, Compose profile `mcp`). It starts only when `TALLYMED_MCP_ENABLED` is exactly `true`; otherwise it prints that it is disabled and exits without listening. The web app has no route to it and the proxy contract above forbids routing to it.
- **Network.** The bind must be a loopback or private-network address (wildcard, hostname and public addresses are refused; a wildcard is allowed only inside a container when `TALLYMED_MCP_CONTAINER=true`). A non-loopback bind additionally requires TLS (1.2 or later), `TALLYMED_MCP_ALLOWED_CIDRS` and `TALLYMED_MCP_ALLOWED_HOSTS`. Every request is checked in this order before any credential lookup: peer address against the allowlist (a loopback listener admits loopback peers only), refusal of `Forwarded`, `X-Forwarded-*`, `X-Real-IP`, `Via` and the web proxy secret header, `Host` against the allowlist, `Origin` refused unless listed, path exactly `/mcp`, method `POST`, a 64 KB body cap and JSON only.
- **Credentials.** `tmcp_` plus 256 random bits, shown once, stored as a SHA-256 digest, scoped (`documents:read`, `records:read`, `documents:content`, `proposals:create`), expiring (at most 365 days) and revocable by an administrator; revocation is permanent and takes effect on the next request (stateless: there is no session to outlive it). Missing, malformed, unknown, revoked and expired credentials get the same 401. Twenty failures a minute from one address block that address for a minute, and each credential is limited to 120 calls a minute (both configurable, per process). Credentials, tokens and document text never appear in logs or audit detail.
- **Database role.** The listener connects as `tallymed_mcp` (created by `setup-role`; migration 0008 defines the grants). It has column-level `SELECT` on the document, bill, visit and adjustment-amount columns the tools return, `INSERT` on proposals and audit rows, and `UPDATE` of its credentials' last-used time. It has no access to accounts, sessions, payments, HSA records, free-text notes or reasons, and no right to change money, documents, attachments or credentials. The listener checks its own privileges at startup and refuses to run as a role that can do more (superuser, table owner, or any extra read or write).
- **Tools.** Five narrow tools only (list unmatched documents, list bills or visits without documents, read a document file, propose a match, list the client's own proposals). Only tools a credential's scopes allow are listed or callable; each service re-checks the scope. Output is bounded (25 items, 2 MB per file by default) and every response states that its text is untrusted data. There is no approve, reject, attach, payment, edit, account or SQL tool. A tool call is audited with the credential, tool and outcome code only.
- **Proposals.** A proposal names one current document version and one bill or visit and pins the versions it was made against; the database allows one proposal ever per document version and record, immutable except for a single decision, and an approval must name the attachment of that exact version and record. Rationales are stripped of control, bidirectional and zero-width characters, limited to 500 characters and rendered as plain text. A client has at most 50 pending proposals (200 per household).
- **Approval.** Only a signed-in person with edit access approves, in the app: the request needs the session, the canonical origin and the CSRF token, and the service locks the record, then the document, then the proposal, and rechecks under those locks that the proposal is pending, its credential is not revoked, the document is not removed and still at the proposed version, the record has not changed since, the document is not already attached there, and that the versions the person was shown match. It then creates the attachment pinned to the reviewed version and marks the proposal approved in one transaction with audit entries for the approval and the attachment, naming the proposal and the credential. A repeated request is a replay; a different request on a decided proposal is refused; simultaneous approvals apply one. Rejection needs a reason and is final.

## Backups and release

Back up PostgreSQL, private document objects and the configuration required for recovery to a protected destination. Create a consistent snapshot or quiesce writes. For documents, take the database dump and the document volume together (database first, then the volume, with uploads paused or the volume snapshotted at the same moment): a volume that is newer than the database only adds unreferenced objects that `cleanup` removes, while a volume older than the database leaves rows without files, which `verify` reports as missing. Encrypt the backup, retain an integrity manifest and protect recovery credentials separately. Restore to an isolated instance, verify database schema, document hashes, ledger totals and access controls, then record the exercise. Document upgrade, rollback limits and recovery steps by release. Keep source links current. Verify secret scanning, dependency checks, redaction, proxy boundary and LAN/auth negatives before a stable tag. The step-by-step commands, the supported proxy topology and the known pre-deployment gaps are in [operations](operations.md). Report security issues through the maintainer's private GitHub reporting channel once enabled, using synthetic evidence.
