# Development and verification

Use Node.js 24, npm, and Docker Compose v2 for the optional container stack. Install the repository's locked dependencies with `npm ci`. Marketing runs on 3000 and the app shell on 3001 when launched through npm. Build outputs live under each application.

## Private app database, first-run setup and checks

The private app needs PostgreSQL and these variables: `DATABASE_URL`, `TALLYMED_CANONICAL_ORIGIN` and optionally `TALLYMED_TRUSTED_PROXIES`, `TALLYMED_SECRETS_KEY` (needed only to store an SMTP password) and `TALLYMED_PROXY_SECRET` and `TALLYMED_SETUP_TOKEN` (see `.env.example`). With the Compose stack running:

```sh
docker compose run --rm web node apps/web/cli/migrate.ts
```

**First administrator.** While no administrator exists, the server accepts a one-time setup token at `/setup` (the sign-in page links there). The token is either the value you set in `TALLYMED_SETUP_TOKEN` (32 to 128 printable characters, at least 16 different ones, no sequential or keyboard runs, repeated blocks, common words or placeholders; `openssl rand -base64 32` is accepted. A rejected value is logged at startup and setup stays closed until it is fixed or emptied; it never affects an installation that already has an administrator) or, when that variable is empty, a random 256-bit token the server generates at startup and prints once to its console (`docker compose logs web`). A generated token lives only in the server's memory: it is never stored in the database, never written to the audit log, never printed again, and a restart before setup finishes generates and prints a new one. Enter the token with the household name, your name, email and a password (12 to 128 characters) at `/setup`, or post the same fields as JSON to `/api/setup` (`setupToken`, `householdName`, `displayName`, `email`, `password`) from a script. The post must carry an `Origin` header equal to `TALLYMED_CANONICAL_ORIGIN` (or a matching `Referer`), or it is refused with `csrf_failed`, for example `curl -X POST -H "Origin: $TALLYMED_CANONICAL_ORIGIN" -H 'Content-Type: application/json' --data @setup.json $TALLYMED_CANONICAL_ORIGIN/api/setup` with the JSON in a file readable only by you; keep the password off command lines and out of logs. After the first administrator exists `/setup` and `/api/setup` answer 404 for everyone, the token stops meaning anything, and nothing is printed at later starts. Ten wrong tokens (five from one trusted client address) lock setup for 15 minutes, including for the right token; restarting the server resets the counters (and replaces a generated token). Someone who can reach the page can keep spending the budget, so if setup stays locked, restart the web process and finish setup while the page is reachable only privately. There is no CLI bootstrap command any more.

**Password change and administrator reset.** An administrator opens Users, chooses Reset password for an account and confirms; the temporary password appears once. Signing in with it goes straight to `/password/change`, the only page that account can use until it picks a new password. Everyone can change their own password on `/account/password`. Settings: `TALLYMED_TEMP_PASSWORD_SECONDS` (300 to 604800, default 14400) and `TALLYMED_PASSWORD_CHANGE_SESSION_SECONDS` (120 to 3600, default 900). The tests are in `tests/web/password-reset.test.mjs`. Extension point for a later self-service email flow: `issueTemporaryCredential` in `apps/web/server/services/credentials.ts` is the only place a temporary credential is created and `password_resets.kind` already reserves `email_temporary`; a delivery channel calls it inside its own transaction with `issuedBy: null`, then delivers the secret. It must add its own per-account and per-address rate limit and must not reveal whether an address has an account. See DECISIONS.md. The dev-up launcher is unchanged (it only creates the first administrator through setup).

**dev-up launcher.** `./dev-up.sh` (POSIX) and `dev-up.cmd` (Windows) start the Compose stack. While no administrator exists they generate a setup token, give it to the web container for that start only and show it on screen once with the `/setup` address. The token is never written to `.env`, a log or a temporary file by the launcher; choosing Start again while setup is still needed shows a new token. If you define `TALLYMED_SETUP_TOKEN` yourself (in `.env` or the environment) the launcher uses it and does not display it. Once an administrator exists the launcher shows no token. Without Compose use `npm run migrate -w @tallymed/web` and start the app with `DATABASE_URL` set; the setup token is printed to that console.

`npm test` also runs the private-app tests. They need a **disposable** PostgreSQL server: set `TALLYMED_TEST_DATABASE_URL` to a URL whose role can create databases (for example `postgres://postgres:...@127.0.0.1:5432/postgres`). Each test file creates and drops its own database. Without the variable those tests are skipped locally and fail in CI. They cover fresh and upgrade migrations, first-run setup (`tests/web/setup.test.mjs`: configured and generated tokens, lockout, concurrent attempts, closed state), sessions, CSRF, authorization, request limits and malicious forwarded headers using fabricated data. After `npm run build`, `npm run test:proxy` starts the built app behind a test TLS proxy, reads the generated setup token from the server console, completes setup and checks HTTPS sign-in, canonical redirects, cookie flags, forged headers, body limits, the absence of an MCP route and the network boundary. It needs `openssl` and the same database variable. The assistant tests (`tests/web/mcp.test.mjs`, `tests/web/proposals.test.mjs`) start the MCP listener on a free loopback port against a disposable database with a temporary restricted role (a role named `tallymed_mcp_t_…` is created and dropped per test, so the server role needs `CREATEROLE`; a superuser has it) and drive it with the MCP SDK client; see [mcp](mcp.md). `npm run test:app-browser` also needs the build: it starts the built app on loopback with a disposable database, creates the first administrator on the setup page, signs in and drives the expense screens in Chromium (members, providers, visits, bills, duplicate warning, adjustments, overview queues) with axe checks and a phone-width overflow check. Set `CHROMIUM_PATH` or run `npx playwright install chromium` first.

Document upload needs a private volume: set `TALLYMED_DOCUMENTS_DIR` to an absolute directory outside the web root (Compose mounts the `documents_data` volume at `/var/lib/tallymed/documents`). Without it the app runs and the Documents screens say storage is not configured. `npm run documents -w @tallymed/web -- verify` and `cleanup [--apply]` check and tidy the volume (see [security](security.md#documents-and-proposals)); restore both the database and the volume, then run `verify`. The document tests (`tests/web/documents*.test.mjs`) use a temporary directory per test and fabricated files built in code.

Copy `.env.example` to `.env` (`Copy-Item .env.example .env` in PowerShell, `cp .env.example .env` in POSIX shells), then run:

```sh
docker compose config --quiet
docker compose up --build -d --wait
curl http://127.0.0.1:3001/healthz
docker compose exec -T db psql -v ON_ERROR_STOP=1 -U tallymed -d tallymed -c "SELECT 1;"
docker compose down
```

Stop the npm web dev server before starting Compose. The web port binds to loopback. PostgreSQL is reachable only on the Compose network, with a named volume. The starter uses the sample password only for a disposable development environment. The health endpoint checks the web process. The separate database command checks PostgreSQL. `docker compose down` keeps the named volume.

`npm test` covers marketing configuration, public roadmap content and brand asset consistency. `npm run build` builds both applications. Follow with `npm run test:export` to check the generated home and roadmap. Browser and performance checks run against the static export, so build marketing first. `npm run test:browser` uses Playwright and axe-core to check the home and roadmap pages at phone, tablet and desktop widths in light and dark schemes, with no horizontal overflow, no accessibility violations, keyboard tab order and visible focus, the preview tab controls, reduced motion, canonical and Open Graph metadata, the sitemap and GitHub links. Install the browser once with `npx playwright install chromium`, or set `CHROMIUM_PATH` to an existing Chromium. `npm run test:performance` enforces gzip byte budgets and checks layout shift, first contentful paint and the absence of third-party requests. `npm run generate:og` regenerates `apps/marketing/public/og.png` from the shared mark. To emulate a repository path, set `NEXT_PUBLIC_BASE_PATH=/tallymed`, `SITE_ORIGIN=https://example.github.io`, and `TALLYMED_REPOSITORY=example/tallymed` before building and testing. These variables must match for both commands. Use the same shells and environment for root and subpath checks. Restart Next after changing build-time settings.

Future app tests use disposable PostgreSQL and fabricated data. Test authorization with real sessions and a second actor, data constraints with real transactions, and core UI workflows in a browser. Use current official specifications when introducing new protocol, framework or tax references. For bugs and contributions, open a GitHub issue with a synthetic reproduction and link the relevant plan. Keep credentials, medical details, financial exports and live backups out of issues, pull requests and CI.

Work branches from `dev` (the default branch) and pull requests target `dev`; `main` is the release branch and publishing is described in [operations](operations.md). For a deployment, set `TALLYMED_SOURCE_URL` to the corresponding source for the running build. See [security and operations](security.md) for the planned reverse-proxy topology and release criteria.

## Server settings, email and trusted proxies (development)

Administrator-editable settings live in the `server_settings` table (migration 0010; one row per group: `general`, `documents`, `email`, `proxy`). `server/settings.ts` reads them at most every five seconds per process and applies them in place to the config object (stored value, then environment, then default). `server/services/settings.ts` holds the admin-only mutations: each re-checks the role, asks for the administrator's password (five wrong answers in 15 minutes lock the check), is optimistic-locked by the group version and audits in the same transaction. Secrets are encrypted by `server/secrets.ts` (AES-256-GCM, HKDF per setting, key from `TALLYMED_SECRETS_KEY`).

Email goes through `server/email.ts` (`isEmailConfigured`, `sendEmail`; see operations.md). To try it locally, run a throwaway mail catcher on port 1025 (for example Mailpit), choose that port, security "None", and tick "Allow loopback and link-local addresses" (from the Compose network use the service name instead). The test suite uses a fake SMTP server (`tests/web/settings.test.mjs`).

The connection address used for the trusted-proxy check is recorded by `installPeerStamp` (called from `instrumentation.ts`), which signs each request's socket address with a per-process key. Tests simulate a connection with `stampPeer(headers, ip)` from `server/peer.ts`. `dev-up` needs nothing new: `dev-up` generates a random `TALLYMED_SECRETS_KEY` into the local `.env` when it is missing (it never prints it); the Compose bridge address of your browser's requests appears on the Reverse proxy page if you want to try the list.
