## Application Foundation decisions (recorded during the milestone)

- **Database access.** `pg` (node-postgres) with parameterized SQL in repositories and plain, numbered SQL migrations run by `apps/web/server/migrate.ts`. No ORM. Migrations are checksummed, applied in transactions under an advisory lock, and tested fresh and as an upgrade from the previous version. Revisit only if a later milestone needs an ORM.
- **Password hashing.** Argon2id via `@node-rs/argon2` defaults.
- **Administrator bootstrap.** A local CLI that reads the password from stdin, closed permanently by `bootstrap_state`. There is no web setup page, so an exposed install cannot be claimed remotely.
- **Provisioning.** Administrators issue single-use invitation links; no email is sent. Roles are `admin` and `operator`.
- **Canonical origin and trusted proxy.** One `TALLYMED_CANONICAL_ORIGIN`, https except loopback. Forwarded headers are trusted only when the request carries `TALLYMED_PROXY_SECRET`, because Next.js route handlers cannot see the TCP peer address. The operator proxy must strip client copies and set the secret. Owner can later replace this with a peer-address allowlist if the server runtime exposes it.
- **Sessions.** Opaque random cookie tokens hashed in PostgreSQL, 12 hour absolute and 2 hour idle lifetimes, `SameSite=Lax`. CSRF uses canonical Origin validation plus a session-bound token. Defaults are configurable by environment variable.
- **Login throttle atomicity (review fix).** The attempt is reserved as a failure inside a short transaction holding advisory locks on the account digest and the trusted address, then verified. Locks are taken account first, address second. Concurrent-burst test proves at most 5 evaluated attempts per account and 20 per trusted address.
- **Failed-login bookkeeping.** Attempt rows are pruned on each sign-in for the keys involved and occasionally globally. Audit stays append-only; failed sign-ins are audited only for existing accounts, once per window plus a lockout event. Unknown addresses are logged without the address.
- **Invitations.** Administrators can revoke an open invitation (audited); re-issuing is revoke then invite again. Duplicate open invitations still conflict.
- **Duplicate JSON keys** are rejected with `invalid_input` by scanning the parsed text, matching urlencoded behavior.
- **Known M01 limitations (owner-visible, not fixed here).** (1) Targeted lockout: anyone who knows an address can lock that account for 15 minutes; a per-account-plus-address key or delay-based throttle is deferred. (2) Without `TALLYMED_PROXY_SECRET` there is no per-address throttle and all clients share the `untrusted` bucket; the server logs a startup warning for https origins and an unauthenticated caller can still add attempt rows by varying the address until they expire (rows are pruned after 1 hour). A global cap on unauthenticated Argon2 work is deferred. (3) No password change or reset exists, and re-invite is blocked once an account exists, so a forgotten password has no in-app recovery; a reset/change flow is planned work for a later milestone. For now an administrator can disable the account and invite a different address. (4) Password policy is length only (12 to 128 characters) with no common-password check. (5) Expired sessions are not pruned. Package `type: module` was added to `apps/web` to remove the Node reparse warning.
- **Server code in TypeScript run by Node.** Service code uses explicit `.ts` import extensions so the CLI and tests execute it with Node type stripping (`erasableSyntaxOnly`).

- **Scheduled before first real deployment.** A password change/reset flow (local reset CLI plus authenticated change) and operator documentation of shared-NAT address lockout and targeted account lockout. Tracked in STATUS.md under M01 acceptance evidence.

## Medical Expense Management decisions (recorded during the milestone)

Starter defaults chosen under the owner's 2026-11-13 preauthorization; flagged in the PR for owner review.

- **Money on the wire and in forms.** Stored as `bigint` cents with range checks (at most $100 billion per amount). Forms and request bodies carry strict USD decimal strings (at most two fractional digits, no exponents, no separators); the service converts them to bigint cents at validation. Read contracts (`billContract`) carry cents as decimal strings. Formatting happens only at the display boundary. No floats anywhere.
- **Responsibility model.** A bill stores the billed amount and a base household responsibility (default: the billed amount, never above it). Household responsibility = base + sum of signed adjustments, always recomputed from rows, never cached. It cannot go below zero (a provider credit needs payments, which are a later milestone). Open balance equals responsibility until payment allocations exist; the field is already published so M03 only subtracts net applied payments.
- **Estimate versus confirmed.** Bills start as `estimate` or `confirmed`. Estimates can be edited and later confirmed once; confirmed amounts never change except through adjustments. Overview totals keep confirmed and estimated sums separate.
- **Adjustments.** Immutable (database triggers). Categories: insurer adjustment, insurer payment, provider discount, financial assistance, correction, and system-set reversal. Each needs a reason, source and effective date. A correction is a linked opposite entry (`reverses_adjustment_id`, unique, so one reversal per adjustment); reversals cannot be reversed. An insurer payment changes responsibility and is not a household cash payment.
- **Concurrency.** Every writer that changes a bill or its adjustments first locks the bill row (`for update`, ids in ascending order; the repository function is `lockBills` and `lockBillsForMoney` in `contracts.ts` is the same function re-exported. Downstream money code imports `lockBillsForMoney`). Responsibility is checked against the locked total, so concurrent adjustments cannot overdraw it. New visits and bills take `for share` locks on the member, provider and visit they reference; archiving takes `for update`, so an archive and a new link cannot interleave. Concurrent tests cover adjustments, reversals, idempotent creates and archive races. Migration 0004 adds database backstops so the same rules hold for direct SQL: a trigger blocks any change to the billed or base amount, the status and the confirmation record of a confirmed bill (and deleting it), and a deferred constraint trigger checks at commit that base + adjustments stays between zero and the maximum (it takes a `no key update` lock on the bill first, so concurrent raw writers are checked one after the other).
- **Idempotency.** `idempotency_records` is unique on (household, actor, operation, key). A bill create, adjustment and reversal claim the key inside their transaction (the unique index serializes concurrent claims), return the stored result id on an exact replay and `conflict` when the key is reused with different input. A rollback removes the claim. Forms embed a fresh random key per render, so a double submit is one effect.
- **Duplicate hints.** Same provider with the same normalized reference (case and punctuation ignored, empty references never match), or same provider, member, statement date and billed amount. Creation returns `duplicate_warning` until the operator ticks "Save anyway". Hints are also shown on lists, the overview and the bill. Nothing is merged automatically. The entry-time reference is normalized by the database with the same expression as the stored `reference_norm` column, so both sides agree for any characters (the expression follows the database locale for non-ASCII case folding, consistently on both sides). The check is advisory: it is a read before the insert, so two concurrent creates of the same bill with different keys can both save.
- **Archive and snapshots.** Members and providers archive and restore (version-guarded). Archived records stay linked and visible; they cannot receive new visits or bills. Visits and bills keep the member and provider names as entered; the UI shows the entry name when the current name differs. Member and visit membership are immutable on a bill (the database enforces that a bill's visit belongs to the bill's member); the billing provider can change while active.
- **Access.** Both roles can read and write expense records for their household (`expenses:read`, `expenses:write`). Another household's record is indistinguishable from a missing one (`not_found`), and composite foreign keys on `(household_id, id)` stop cross-household links in the database.
- **Routing.** All expense mutations post to `/api/expenses/<action>` through the shared POST pipeline (transport, origin, bounded body, session, CSRF), with the action chosen from a fixed allow-list. Validation errors redirect back with only an error code in the URL. The typed values (for example a date of birth or notes) travel in a two-minute HttpOnly flash cookie that only the target page can read and only while it shows an error, so they stay out of access logs, history and Referer headers (never the CSRF token or idempotency key).
- **Pagination.** Keyset cursors (opaque, validated) with stable sort: members and providers by name, visits and bills by date descending then id. Select lists load at most 100 records, always include the record that is currently selected (so saving never silently reassigns a provider or unlinks a visit), say when they are truncated and offer a search (`providerQ`, `memberQ`, `visitQ`) to reach the rest. Member, provider and visit lists are not a typeahead; revisit for very large households.
- **Attachment contract.** Downstream documents target `bill`, `visit` or `bill_adjustment` by UUID via `resolveAttachmentTarget`. M05 should use composite foreign keys on `(household_id, <id>)`. See docs/contracts.md.
- **Bill edit audit.** `bill.updated` records from and to values for provider, reference, statement and due dates, amount source, source note and cents. Free-text notes record only a changed flag.
- **Known limitations (review notes, accepted for M02).** Reversal entries use the server's UTC date, which can be the next day for a US evening user until households have a time zone. Audit, adjustment and creation timestamps are transaction-start `now()`, so under heavy concurrency history order follows transaction start rather than lock order (the audit id sequence is the commit-independent tiebreaker to consider). Member, provider and visit creates are not idempotent (a double submit makes two records); bills, adjustments and reversals are. Overview totals and queues are read on separate connections and can disagree momentarily after a write. The reversal of an earlier adjustment can be blocked by a later offsetting entry; the user must reverse the later one first.
- **Not in this milestone.** Payments, refunds, plans, HSA, document storage and export. No public roadmap change.
