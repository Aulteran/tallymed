## Application Foundation decisions (recorded during the milestone)

- **Database access.** `pg` (node-postgres) with parameterized SQL in repositories and plain, numbered SQL migrations run by `apps/web/server/migrate.ts`. No ORM. Migrations are checksummed, applied in transactions under an advisory lock, and tested fresh and as an upgrade from the previous version. Revisit only if a later milestone needs an ORM.
- **Password hashing.** Argon2id via `@node-rs/argon2` defaults.
- **Administrator bootstrap.** Superseded by the setup token decision below (the original local CLI and "no web setup page" rule were replaced at the owner's request). Closing is still permanent through `bootstrap_state`.
- **Provisioning.** Administrators issue single-use invitation links; no email is sent. Roles are `admin` and `operator`.
- **Canonical origin and trusted proxy.** One `TALLYMED_CANONICAL_ORIGIN`, https except loopback. Forwarded headers are trusted only when the request carries `TALLYMED_PROXY_SECRET`, because Next.js route handlers cannot see the TCP peer address. The operator proxy must strip client copies and set the secret. Owner can later replace this with a peer-address allowlist if the server runtime exposes it.
- **Sessions.** Opaque random cookie tokens hashed in PostgreSQL, 12 hour absolute and 2 hour idle lifetimes, `SameSite=Lax`. CSRF uses canonical Origin validation plus a session-bound token. Defaults are configurable by environment variable.
- **Login throttle atomicity (review fix).** The attempt is reserved as a failure inside a short transaction holding advisory locks on the account digest and the trusted address, then verified. Locks are taken account first, address second. Concurrent-burst test proves at most 5 evaluated attempts per account and 20 per trusted address.
- **Failed-login bookkeeping.** Attempt rows are pruned on each sign-in for the keys involved and occasionally globally. Audit stays append-only; failed sign-ins are audited only for existing accounts, once per window plus a lockout event. Unknown addresses are logged without the address.
- **Invitations.** Administrators can revoke an open invitation (audited); re-issuing is revoke then invite again. Duplicate open invitations still conflict.
- **Duplicate JSON keys** are rejected with `invalid_input` by scanning the parsed text, matching urlencoded behavior.
- **Known M01 limitations (owner-visible, not fixed here).** (1) Targeted lockout: anyone who knows an address can lock that account for 15 minutes; a per-account-plus-address key or delay-based throttle is deferred. (2) Without `TALLYMED_PROXY_SECRET` there is no per-address throttle and all clients share the `untrusted` bucket; the server logs a startup warning for https origins and an unauthenticated caller can still add attempt rows by varying the address until they expire (rows are pruned after 1 hour). A global cap on unauthenticated Argon2 work is deferred. (3) No password change or reset exists, and re-invite is blocked once an account exists, so a forgotten password has no in-app recovery; a reset/change flow is planned work for a later milestone. For now an administrator can disable the account and invite a different address. (4) Password policy is length only (12 to 128 characters) with no common-password check. (5) Expired sessions are not pruned. Package `type: module` was added to `apps/web` to remove the Node reparse warning.
- **Server code in TypeScript run by Node.** Service code uses explicit `.ts` import extensions so the CLI and tests execute it with Node type stripping (`erasableSyntaxOnly`).

- **Scheduled before first real deployment.** A password change/reset flow (local reset CLI plus authenticated change) and operator documentation of shared-NAT address lockout and targeted account lockout. Tracked in STATUS.md under M01 acceptance evidence.

## Medical Expense Management decisions (recorded during the milestone)

Starter defaults chosen under the owner's 2026-11-13 preauthorization; flagged in the PR for owner review.

- **Money on the wire and in forms.** Stored as `bigint` cents with range checks (at most $100 billion per amount). Forms and request bodies carry strict USD decimal strings (at most two fractional digits, no exponents, no separators); the service converts them to bigint cents at validation. Read contracts (`billContract`) carry cents as decimal strings. Formatting happens only at the display boundary. No floats anywhere.
- **Responsibility model.** A bill stores the billed amount and a base household responsibility (default: the billed amount, never above it). Household responsibility = base + sum of signed adjustments, always recomputed from rows, never cached. It cannot go below zero (a provider credit needs payments, which are a later milestone). Open balance equals responsibility until payment allocations exist; the field is already published so M03 only subtracts net applied payments.
- **Estimate versus confirmed.** Bills start as `estimate` or `confirmed`. Estimates can be edited and later confirmed once; confirmed amounts never change except through adjustments. Overview totals keep confirmed and estimated sums separate.
- **Adjustments.** Immutable (database triggers). Categories: insurer adjustment, insurer payment, provider discount, financial assistance, correction, and system-set reversal. Each needs a reason, source and effective date. A correction is a linked opposite entry (`reverses_adjustment_id`, unique, so one reversal per adjustment); reversals cannot be reversed. An insurer payment changes responsibility and is not a household cash payment.
- **Concurrency.** Every writer that changes a bill or its adjustments first locks the bill row (`for update`, ids in ascending order; the repository function is `lockBills` and `lockBillsForMoney` in `contracts.ts` is the same function re-exported. Downstream money code imports `lockBillsForMoney`). Responsibility is checked against the locked total, so concurrent adjustments cannot overdraw it. New visits and bills take `for share` locks on the member, provider and visit they reference; archiving takes `for update`, so an archive and a new link cannot interleave. Concurrent tests cover adjustments, reversals, idempotent creates and archive races. Migration 0004 adds database backstops so the same rules hold for direct SQL: a trigger blocks any change to the billed or base amount, the status and the confirmation record of a confirmed bill (and deleting it), and a deferred constraint trigger checks at commit that base + adjustments stays between zero and the maximum (it takes a `no key update` lock on the bill first, so concurrent raw writers are checked one after the other).
- **Idempotency.** `idempotency_records` is unique on (household, actor, operation, key). A bill create, adjustment and reversal claim the key inside their transaction (the unique index serializes concurrent claims), return the stored result id on an exact replay and `conflict` when the key is reused with different input. A rollback removes the claim. Forms embed a fresh random key per render, so a double submit is one effect.
- **Duplicate hints.** Same provider with the same normalized reference (case and punctuation ignored, empty references never match), or same provider, member, statement date and billed amount. Creation returns `duplicate_warning` until the operator ticks "Save anyway". Hints are also shown on lists, the overview and the bill. Nothing is merged automatically. The entry-time reference is normalized by the database with the same expression as the stored `reference_norm` column, so both sides agree for any characters (the expression follows the database locale for non-ASCII case folding, consistently on both sides). The check is advisory: it is a read before the insert, so two concurrent creates of the same bill with different keys can both save.
- **Archive and snapshots.** Members and providers archive and restore (version-guarded). Archived records stay linked and visible; they cannot receive new visits or bills. Visits and bills keep the member and provider names as entered; the UI shows the entry name when the current name differs. Member and visit membership are immutable on a bill (the database enforces that a bill's visit belongs to the bill's member); the billing provider can change while active.
- **Access.** Both roles can read and write expense records for their household (`expenses:read`, `expenses:write`). Another household's record is indistinguishable from a missing one (`not_found`), and composite foreign keys on `(household_id, id)` stop cross-household links in the database.
- **Routing.** All expense mutations post to `/api/expenses/<action>` through the shared POST pipeline (transport, origin, bounded body, session, CSRF), with the action chosen from a fixed allow-list. Validation errors redirect back with only an error code in the URL. The typed values (for example a date of birth or notes) travel in a two-minute HttpOnly flash cookie that only the target page can read and only while it shows an error, so they stay out of access logs, history and Referer headers (never the CSRF token or idempotency key).
- **Pagination.** Keyset cursors (opaque, validated) with stable sort: members and providers by name, visits and bills by date descending then id. Select lists load at most 100 records, always include the record that is currently selected (so saving never silently reassigns a provider or unlinks a visit), say when they are truncated and offer a search (`providerQ`, `memberQ`, `visitQ`) to reach the rest. Member, provider and visit lists are not a typeahead; revisit for very large households.
- **Attachment contract.** Downstream documents target `bill`, `visit` or `bill_adjustment` by UUID via `resolveAttachmentTarget`. M05 should use composite foreign keys on `(household_id, <id>)`. See docs/contracts.md.
- **Bill edit audit.** `bill.updated` records from and to values for provider, reference, statement and due dates, amount source, source note and cents. Free-text notes record only a changed flag.
- **Known limitations (review notes, accepted for M02).** Reversal entries use the server's UTC date, which can be the next day for a US evening user until households have a time zone. Audit, adjustment and creation timestamps are transaction-start `now()`, so under heavy concurrency history order follows transaction start rather than lock order (the audit id sequence is the commit-independent tiebreaker to consider). Member, provider and visit creates are not idempotent (a double submit makes two records); bills, adjustments and reversals are. Overview totals and queues are read on separate connections and can disagree momentarily after a write. The reversal of an earlier adjustment can be blocked by a later offsetting entry; the user must reverse the later one first.
- **Not in this milestone.** Payments, refunds, plans, HSA, document storage and export. No public roadmap change.

## Payments and Payment Plans decisions (recorded during the milestone)

Starter defaults chosen under the owner's 2026-11-13 preauthorization; flagged in the PR for owner review.

- **Ledger shape.** Payments, allocations, refunds and reversals are immutable rows. `payment_entries` is one signed ledger per payment (allocation, allocation reversal, refund, unapplied refund, refund reversal) so a single set of commit-time guards covers every limit. Corrections are linked entries with a reason; nothing is edited or deleted (triggers enforce it, including truncate).
- **Applied cash is limited to confirmed bills and open balances.** The service rejects an allocation above a bill's open balance and any allocation to an estimate. Extra cash stays unapplied and visible. A provider credit (negative balance) arises only when a later adjustment lowers responsibility below applied payments, and is shown separately from cash. The database refuses any new allocation or refund reversal that would push net applied cash above the bill's open balance, so a credit never comes from a payment write. A cash refund is always an explicit event and never inferred from a lower statement total.
- **Allocation correction versus refund.** Moving applied cash back to unapplied (wrong bill) is a correction that does not touch cash. A refund records cash the provider returned: it lowers net applied cash, raises the bill balance and lowers net cash paid. Both can be partial. A refund reversal exactly offsets one refund, once. Voiding a payment is allowed only when nothing is applied or refunded.
- **Commit-time guards (M02 carry-forward).** Deferred constraint triggers re-check, after taking the payment row lock: unapplied cash never negative, applied plus refunds never above the payment, each allocation between zero and its original amount, a voided payment holding nothing, installment matches within the installment (race-safe: the installment row is locked first) and within the allocation's net cash across plans, no negative net match per installment and allocation, matches only to the current revision of an active plan, applied cash within each bill's open balance (the bill row is locked first), plan bills of one provider with confirmed amounts, and schedule revisions totalling their installments. A before-insert trigger validates reference rules (targets are allocations of the same payment and bill, only confirmed bills receive cash, refund reversals exactly offset one refund). Direct SQL tests prove each, including concurrent raw writers.
- **Locking and retries.** One global lock order for services and guards: payments (ascending id), then bills (ascending id), then plans (ascending id). Operations that touch several plans or payments collect the set first and lock it sorted (refunds and allocation reversals lock every affected plan once, before writing; plan changes lock the plan's matched payments before the plan and, if a match for a new payment appears under the plan lock, restart the transaction (`RetryTransaction`) so nothing is ever locked out of order). Reads of balances happen only afterward. A whole-transaction retry on deadlock or serialization failure (40P01, 40001) is a backstop only; tests assert that no retry was needed under opposing multi-payment writers. Database check violations map to `conflict`.
- **Idempotency.** Every money write claims an idempotency record inside its transaction (the shared helper moved to `services/support.ts`). Exact replays return the stored result; changed input conflicts; a rollback releases the claim. Forms embed a fresh key per render.
- **Plans are obligations.** A plan covers one or more confirmed bills of one provider (default: one provider per plan; bills cannot be added after creation). Schedules are generated (total, count, first due date, weekly, biweekly or monthly cadence, exact cent split with extra cents on the earliest installments, month-end clamped from the first day) or listed explicitly (JSON, custom cadence). The plan total is not forced to equal bill balances (fees and partial scope are possible); the plan page shows both.
- **Matching.** A match references an allocation of one of the plan's bills, can be partial, and never exceeds the installment's unpaid amount or the allocation's unmatched net cash across all plans. Removing a match is a signed linked entry with a reason. A refund or allocation reversal automatically releases excess matches (audited, latest due date first) so matches never count cash the household no longer holds.
- **Revisions.** A revision is a new immutable schedule with a reason. Matches carry forward in due-date order onto the new installments as rows marked carried; earlier revisions are untouched. A revision cannot drop below what is matched. Cancelling a plan keeps all history and removes it from the due queues. Cancelling is final.
- **Schedule input modes, remainder and keep-paid revisions (owner request, 2026-11).** A plan or revision can be entered as a count at a total price, or at an amount per installment (count x amount without rounding; or a total and an amount with the count derived and a smaller last installment). Leftover cents go to the earliest installments by default (unchanged), or all to the last, or as a smaller last installment. Warnings never block: total mismatch (entered total versus count x amount), plan versus bill balance (plan total minus matched cash against the covered bills' open balance, signed, so credits work) and rounding differences. They are recorded as codes in the audit detail and the plan page shows the balance warning live. A keep-paid revision keeps fully paid installments and restarts the rest; matches follow kept installments by identity because the greedy carry-forward would otherwise put an old partial match on a kept line. No migration. Starter choices flagged for owner review: the balance-warning basis, ignoring the remainder choice in per-installment mode, a keep-paid revision refused when everything is already paid, and the revision cadence becoming Custom. Needs the independent financial review that carry-forward changes require.
- **Status and clocks.** Installment status (paid, partial, unpaid, overdue) is derived from posted rows and an `asOf` date, UTC by default (households have no time zone yet). Screens and tests pass the date explicitly; no test depends on transaction-start timestamps. Ledger and history order use identity sequences and audit ids.
- **Matching existing payments (post-M07 addition).** Creating a plan can tick several bills of the plan's provider (a form sends one `bill_<id>` checkbox per bill; JSON sends `billIds`) and can match cash already applied to them. A plan page also offers "Match all existing payments". Both fill the earliest installments that still owe with unmatched allocation cash, oldest payment first, as ordinary match rows (references only: no payment, allocation or balance changes). Cash matched to another plan's current schedule is never reused. Payments are locked first, then bills, then the plan; a payment that appears after the locks restarts the transaction. The first due date may be in the past. A plan also has a `started_on` date (migration 0012; UTC calendar date, defaults to today, never in the future, existing plans take their recorded date). It is a label and the cut-off for matching: only payments made on or after it are matched, by both the create option and the bulk action. The real entry time stays in `created_at` and the audit trail (`plan.created` records `startedOn`). Still one provider per plan (database trigger); bills of different providers need a separate plan or a model decision. Needs an independent financial review.
- **Access.** Payments and plans use the existing `expenses:read` and `expenses:write` capabilities (both roles); another household's record is `not_found`. Actions post through the shared pipeline at `/api/expenses/payments/*` and `/api/expenses/plans/*`.
- **Audit.** Every money event records before and after values (balance, allocation, unapplied cash, net cash, installment matched). Reasons and notes stay on the immutable entry and are not copied into audit detail.
- **Pool hardening.** The pg pool has an `error` listener that logs by error code only, so an idle connection lost to a database restart no longer raises an unhandled event.
- **Net allocation contract.** `listNetAllocations` returns a page with `nextCursor`; callers that need every row must follow cursors, so a result is never silently truncated. As-of dates must be real calendar dates.
- **Known limitations (owner-visible).** Cancelling a plan is final. Raw SQL writers that touch several bills in one transaction must lock bills in ascending id order themselves; the guards serialize per bill but cannot reorder a writer's own statements. The payable-bill pick keeps the current bill but lists at most 100. Payments, refunds and matches cannot be created from the MCP or documents (later milestones). No bulk import. A plan cannot gain bills after creation. Refund-event and ledger screens show entries, not a monthly cash report. A reversal date for refunds is entered by the user; allocation reversals and voids default to the UTC date in forms. Matches are made one installment at a time. Unapplied cash has no aging. HSA eligibility and reimbursements are not here (M04). The password change and reset flow and shared-NAT lockout documentation from M01 remain required before a real deployment.

## HSA Reimbursements decisions (recorded during the milestone)

Starter defaults chosen under the owner's 2026-11-13 preauthorization; flagged in the PR for owner review.

- **Ledger shape.** Four immutable tables (triggers refuse update, delete and truncate): `hsa_eligibility_decisions`, `hsa_claims`, `hsa_receipts` and one positive-amount ledger `hsa_entries` (`reserve`, `receipt`, `external_receipt`, `receipt_reversal`, `reject`, `cancel`, every amount positive, effect by kind). One set of commit-time guards covers every limit. Figures are never cached: the `hsa_allocation_status` view derives them from posted rows on top of the M03 `allocation_net` view. HSA tables never write `payment_entries`, so an HSA receipt cannot change a bill, payment, plan or provider balance (tested against the full payment snapshot).
- **Eligibility is a decision, not an inference.** Statuses are eligible (an eligible amount above zero), ineligible and pending; no decision means unknown. Eligible and ineligible decisions require a rationale and an evidence type and reference (receipt, EOB, statement, provider letter, plan document, other); pending needs only a rationale. A date, category or suggestion alone cannot certify (the schema and the database check enforce evidence). Decisions are immutable; the newest is current and the earlier ones stay in the history. A form carries the number of decisions it saw, and a stale form is refused (`stale_version`). "Household-configured eligibility context" is a free-text plan-context note on each decision (plan year, account used); there is no settings screen for it (owner-visible default).
- **Ceiling and formulas.** Ceiling = least(current decision's eligible cents, the allocation's net cash from `allocation_net`), so a refund or reversal lowers it automatically ("recompute eligibility from the remaining covered cash"). Pending = reserves - receipts - rejects - cancels. Received = receipts + external receipts - receipt reversals. Available = max(0, ceiling - pending - received). Needs review = max(0, pending + received - ceiling). A decision cannot name more than the net cash at the time (checked under the payment lock and again at commit).
- **Needs review freezes, never rewrites.** Refunds, allocation reversals and lower decisions after claims are allowed and never edit history. Excess shows as needs review, and the commit-time guard refuses any new reservation or external receipt while pending plus received is above the ceiling (this is the freeze). Receipts against already-reserved lines, releases (cancel or reject), receipt reversals and new decisions stay possible, and those are the ways to resolve it: release pending amounts, reverse a returned receipt, or record a new decision with evidence. There is no separate "mark resolved" action; the state clears when the figures fit.
- **Claims are a record, not a submission.** A claim has a submitted date, an administrator name, an optional reference (unique per household, case-insensitive, so the same administrator claim cannot be recorded twice) and lines of one reservation per allocation. TallyMed does not send claims. Duplicate protection also comes from the ceiling (a duplicate reservation cannot exceed what is available) and from idempotency keys.
- **Line statuses with history.** Submitted, partially fulfilled, fulfilled, rejected, canceled are derived from the line's entries, never stored. A line paid in part with the rest released shows partially fulfilled; a fully released unpaid line shows rejected or canceled. A release can be partial; the default releases all that is still reserved.
- **Receipts.** A receipt is fully allocated: its amount equals the sum of its lines (a split), a line can be paid by several receipts (partial payments), and each line amount is limited to what the line still has reserved. Received cash moves pending to received. Reversal covers a whole receipt with linked entries, once (unique index). A reversal lowers received and does not restore pending, as the ledger formulas define, so the amount becomes available to claim again.
- **External reimbursements.** A reimbursement not claimed here is a receipt with origin external. It needs a source and evidence (database check) and, as the owner-visible default, must fit the amount still available like a claim. For money that already arrived against an undecided or ineligible payment, record the eligibility decision first.
- **Locking and retries.** HSA writers lock the payments behind their allocations (ascending id) through `lockPaymentsForMoney` before reading any figure and take no bill or plan lock, so they can never invert the global order (payments, bills, plans). The guards lock the payment row first (`for no key update`) in their own statement, then re-check, the same parent-first pattern as M03; a refund that commits after a claim is allowed and shows as needs review, and a claim that commits after a refund is refused. Retry is a backstop; tests assert `retryStats.lockConflicts` stays 0 under opposing multi-payment claims racing refunds. Raw SQL writers that touch several payments in one transaction must lock payments in ascending id order themselves.
- **Idempotency and audit.** Operations: `hsa.decide`, `hsa.claim`, `hsa.release`, `hsa.receipt`, `hsa.external_receipt`, `hsa.receipt_reverse`; exact replay returns the first result, changed input conflicts, rollback releases the claim. Every write records audit events with before and after ceiling, pending, received, available and needs-review cents per allocation; reasons, notes, evidence text and references are not copied into audit detail.
- **Reporting and export.** HSA totals and the allocation list share one filter (family member, provider, payment date range, state) and one definition, and the totals row is one statement, so every figure comes from one snapshot. The scoped export is a GET returning CSV from one repeatable-read snapshot: `allocations` (one row per payment plus a TOTAL row equal to the sum), `events` (every entry with its signed effect on pending and received, so figures rebuild from history) and `decisions`. Text cells that could be read as formulas are prefixed with a quote, exports are capped at 20,000 rows (fail closed with a message to narrow the scope) and each export is audited with its kind and row count. Filters use payment dates, not statement dates; the overview says so.
- **Access.** HSA uses the existing `expenses:read` and `expenses:write` capabilities; another household's record is `not_found`. Actions post through the shared pipeline at `/api/expenses/hsa/*`; the export is `GET /api/hsa/export`.
- **Known limitations (owner-visible).** No document attachments to evidence yet (M05 adds attachment targets; for now evidence is a typed reference). No tax-year contribution limits, plan-year rules or tax treatment: eligibility is the user's decision. Receipts are reversed whole, not in part (reverse and re-record). Claims and decisions cannot be edited, only superseded or released. Overview HSA tiles and queues use the member and provider filters but not the statement-date filters. A voided or fully reversed payment leaves its HSA rows in place as needs review until the person resolves them. A claim reference stays reserved after its claim is canceled or fully released (unique per household, case-insensitive), so a reused administrator reference needs a new reference or a note; references that differ only by look-alike Unicode characters are different references. A line whose receipts were all reversed and that has nothing pending or released shows the status Receipt reversed and its claim is closed at $0 received. A receipt header cannot be committed without entries that add up to its amount (commit-time guard). The password reset flow and shared-NAT lockout documentation from M01 still apply before a real deployment.

## Document Management decisions (recorded during the milestone)

Owner-visible starter choices, picked conservatively under the owner's 2026-11-13 preauthorization for M05 and flagged in the PR description. The owner can change any of them.

- **Allowed formats: PDF, PNG and JPEG only.** Verified by content (structure, checksums and end markers), not by extension or declared type; a declared type or extension that disagrees with the content is refused. No HEIC, WebP, TIFF, Office files, archives or SVG. A PDF with scripts, launch actions, embedded files, rich media, form submission, encryption or a ZIP trailer is refused on a best-effort basis, not as a guarantee: the file is tokenized in one linear pass as a reader would (comments, strings, names, dictionaries and stream bodies are recognised, so a name counts only where it is a name), every object stream is inflated within a 16 MB budget and tokenized the same way, and anything that cannot be parsed unambiguously is refused (unbalanced delimiters, unterminated strings, a stream without a dictionary or `endstream`, an object stream with a filter chain, another filter or a predictor, corrupt data, more than 4096 object streams). Names refused: JavaScript, JS, Launch, EmbeddedFile(s), EF, FileAttachment, RichMedia, OpenAction, AA, XFA, SubmitForm, ImportData, GoToR, GoToE, Encrypt. Other hiding places may exist, so downloads are attachment-only and sandboxed, and a saved PDF opened in a local reader should be treated as untrusted. Encrypted PDFs are refused because their content cannot be checked; the person can upload an unlocked copy.
- **Size cap: 10 MB per file** (configurable 1 to 25 MB) and **2 GB per household** (configurable), checked under a per-household advisory lock so concurrent uploads cannot overshoot. Images are capped at 50 megapixels.
- **Private volume and backup strategy.** Bytes live in a directory on a private volume (`TALLYMED_DOCUMENTS_DIR`, Compose named volume `documents_data`), never in PostgreSQL and never under the web root. Backup is the database dump plus the volume, taken together; `verify` compares stored files with the recorded size and SHA-256 after a restore. No object-store (S3) adapter yet; `ObjectStore` is the seam for one.
- **Write order.** Validate, write to quarantine, read back and compare the checksum, promote, then record rows in one transaction. A failure removes the object; a crash leaves an unreferenced object that `cleanup --apply` removes after a 24-hour grace period counted from promotion. Rows never point at unverified bytes. Quarantine and the grace period are storage states; the database has no pending state, so there is no row to recover.
- **Versions.** Each upload to a document adds an immutable version (SHA-256, size, media type, display name). An attachment is pinned to the version the person saw (the attach forms send `<document id>@<version>` and a newer version is refused as stale; API callers may omit the version and get the current one), so a record's evidence never changes under it. Re-pointing a record at a newer version is detach then attach, and both links stay in the history. Identical bytes in the same household are flagged (a duplicate warning the person can confirm past), never merged.
- **Attachment types.** `bill`, `visit`, `bill_adjustment`, `hsa_receipt` and `hsa_eligibility_decision`, one nullable composite foreign key per type with a `check` that exactly the matching column is set, so the database enforces the household boundary. A document can be attached to many records and a record can have many documents; the same pair is attached at most once at a time (partial unique index). Payments, claims and plans are not targets in this milestone (add a type later, one writer per change).
- **Unmatched queue.** A document with no active link and no removal. It is derived, not stored, so it can never disagree with the links.
- **Link history.** Attachments are never deleted; detaching records who, when and why. Every attach and detach is audited with before and after link counts and queue membership; checksums are recorded for uploads and versions; titles, notes, reasons and file names are not copied into audit detail.
- **Removal.** A tombstone, allowed only when no active link exists (service check plus a deferred database guard that also covers a racing attach). Bytes are purged by `cleanup` after 30 days (configurable); metadata, checksum and history stay forever. There is no restore action in the app. Within the window an operator can restore a document in one maintenance transaction that disables the `documents_guard_change` trigger, clears `removed_at`, `removed_by` and `removal_reason`, and re-enables the trigger (the procedure is in security.md and is tested); it is not a casual UPDATE, because the trigger refuses one. A detached link to a removed document stays in the record's link history, marked as removed.
- **Locking.** Document writers take the parent record first (a bill with the global money lock, other targets key-share), then the document row, and never a payment or plan lock; the concurrency tests assert `retryStats.lockConflicts` stays zero beside payment and adjustment writers.
- **Download.** Authenticated, household scoped, integrity verified before sending, safe headers (see security.md). PDFs are never rendered inline. Each download is audited with document and version only.

Known limitations (owner-visible):

- Removal does not free quota until the purge (bytes of removed documents still count); the owner can run `cleanup --apply` with a shorter `TALLYMED_DOCUMENT_RETENTION_DAYS` to free space sooner.
- After a restore, run `verify` and read its `unreferenced` list before `cleanup --apply`: a volume restored with old file times onto an older database dump has files the database does not know. `cleanup` refuses the common mismatches, but only `verify` tells you which files they are.
- Refused uploads are not audited or logged as a security signal; only successes are audited.
- JPEGs may carry up to 64 KB of zero padding after the end marker; any other trailing byte is refused (the strict choice will occasionally refuse an odd real file).
- No malware scanning and no OCR or text extraction; documents are treated as opaque, untrusted files.
- Upload abuse is bounded: 4 concurrent uploads per process, at most 30 upload attempts per person per minute (in memory, per process; accepted or refused), 10 MB per file, a 16 MB inflate budget (about 0.3 s of synchronous scanning at worst). Any repeated dictionary key is refused as ambiguous (readers disagree about which counts), as is a direct `/Length` that ends after an earlier `endstream`, and an object stream needs a direct, verified `/Length`. `/OpenAction` is allowed only with an array (view destination). PDFs with more than 16 MB of object-stream data are refused (print to PDF to produce a simpler copy).
- The PDF active-content check is best-effort and a reader may still parse a crafted file differently from the scan (see Allowed formats); the attachment-only download, `nosniff` and the sandbox policy are the real controls. Image polyglots remain possible (a JPEG may carry arbitrary bytes after its scan header, PNG ancillary chunks can carry data); they are served with a fixed image type, `nosniff` and a sandbox policy.
- `cleanup` is a dry run unless `--apply` is given, and refuses to apply when the database does not appear to match the volume (most old files unreferenced, or no versions at all) unless `--force`. Run `verify` first after any restore.
- At most four uploads run at once per process (more get a 429 `busy`); bytes reach the quarantine before the quota check, so the transient disk use is bounded by that cap times the file limit.
- Uploads are buffered in memory (at most 10 MB plus 64 KB, several copies while parsing) before validation; the proxy should enforce the same body limit.
- Storage space is limited per household by a quota but there is no per-user rate limit on uploads.
- Cleanup and verify are operator commands to be scheduled; nothing runs them automatically, and no backup automation exists yet (documented procedure only).
- The attach picker lists the newest 50 documents (with a title and file-name search); an existing document is also attachable from its own page by record ID.
- Removed-document bytes cannot be restored from the UI, and a purged version is gone unless it is in a backup.
- The identical-content hint is not race-free (two simultaneous uploads of the same bytes can both succeed); it is a hint, not an invariant.
- Not verified here: a real reverse proxy's upload limits, large-file behaviour through the proxy, a real device camera upload, and a screen-reader pass.
- **Accepted limitations at M05 acceptance (owner-visible).** Security N3: the PDF scan skips ordinary stream bodies, so a fake object hidden in one plus a bogus `startxref` passes, and a lenient reader that rebuilds the cross-reference table could parse it; accepted as best-effort because downloads are attachment-only, `nosniff` and sandboxed. A reader that treats `\x0b` after a name as a delimiter can also parse differently. Scanning runs on the main thread (about 0.4 s worst case per upload; move it to a worker if households share a host). The upload rate limit is per process and blocks a legitimate bulk import of more than 30 files a minute. The password change and reset flow and shared-NAT lockout documentation from M01 remain required before a real deployment.

## Optional AI Assistance decisions (recorded during M06)

Owner-visible starter choices, picked conservatively and flagged in the PR description. The owner can change any of them. M06 started on the owner's explicit request ("Go ahead and do M06", 2026-11-13); the earlier M01 to M05 preauthorization did not cover it.

- **Transport and SDK.** The maintained TypeScript MCP SDK (`@modelcontextprotocol/sdk` 1.32.2, pinned) over streamable HTTP in stateless JSON mode: one `POST /mcp` per request, no sessions, so revocation and expiry apply on the next request. Credentials are an `Authorization: Bearer` token, which the SDK's own client transports send; no OAuth flow (a single-household LAN service has no authorization server). Clients that only speak stdio use a bridge such as `mcp-remote`.

It connects as `tallymed_mcp` with column-level read grants and insert on proposals and audit rows only, applied by `tallymed_apply_mcp_grants` (migration 0008) through `setup-role`, which is the only place a role password is chosen. Startup refuses a role with more access. Trade-off: the grants must be re-applied (`setup-role`) after a migration that adds columns the tools need.

Only the tools a credential's scopes allow are listed. At most ten usable credentials per household, lifetime 1 to 365 days (default 90).

Approval is refused when either changed, the document was removed, the pair is already attached, the credential was revoked, or the reviewer's view differs. A stale proposal can only be rejected; a fresh suggestion for the new version is allowed because the uniqueness key is (document, document version, record).
- **One suggestion per document version and record, ever.** A rejected pair cannot be re-raised by the same or another client for that document version. This is a deliberate guard against a client pestering the reviewer; a new document version reopens it.

These limits are per process (in memory) except the pending caps, which are enforced in the database under a household lock.
- **Approval path.** Any signed-in member who can edit records (administrator or operator) can approve or reject; only administrators manage credentials. Approval reuses the M05 attachment insert, so the attachment is an ordinary pinned link that can be detached with the usual history.
- **Database defence in depth (review findings).** The MCP role cannot read `decision_note`, `decided_by` or `attachment_id` of proposals. A BEFORE INSERT trigger makes every new proposal pending and undecided, and a trigger on `audit_events` limits the role (recognised by being unable to read accounts) to its own `mcp.*` and `proposal.created` rows with no acting user. The startup check compares every column's privileges with an allow-list, not a few spot checks. The role is not scoped to a household: household isolation rests on the listener's `household_id`-scoped queries, which suits the single-household self-hosted design.
- **Reviewer-view revision.** The approval form carries the document row's revision as well as the file version and record version, so an edit to a document's title, kind or note after the reviewer opened the page refuses the approval and asks them to reload. Payments do not bump `bills.version`, so a proposal is not stale because of payments alone; approval is evidence-only either way. An expired credential's pending proposals can still be approved by a person (only revocation blocks approval).
- **Audit.** Tool calls are audited by credential, tool and outcome code only; creating, approving and rejecting are audited with ids and codes; no titles, notes, rationales, file names or tokens appear in audit detail or logs.
- **Untrusted text.** Titles, notes, file names, record text and rationales are returned and stored as data, wrapped by a notice in every response; client text is stripped of control, bidirectional and zero-width characters, limited to 500 characters and rendered only as React text (a test fails on any raw-HTML rendering API in the app).

## First-run setup token decision (owner request, after M07)

- **Replaces the bootstrap CLI.** The owner disliked the local bootstrap command and the "no web setup page" login screen. The first administrator is now created on a web setup page (`/setup`, `POST /api/setup`) by presenting a one-time setup token. `apps/web/cli/bootstrap.ts`, `npm run bootstrap` and the `TALLYMED_BOOTSTRAP_*` variables are removed rather than kept: the endpoint covers scripted installs (JSON post), and anyone with the database credentials needed by a CLI could already create rows directly, so a second path only added surface and documentation.
- **Token source.** `TALLYMED_SETUP_TOKEN` when set (32 to 128 printable characters, at least 16 distinct, no run of 5 sequential characters or keyboard-row fragment, no repeated 8-character block, no common word or placeholder; `openssl rand -base64 32` passes (a 64-character hex value is rejected about a quarter of the time by the distinct-character rule: use base64). Review N1 showed a bare length rule accepted `abcdefghijklmnopqrstuvwxyz` and `correct-horse-battery-staple`. An invalid value never stops the app (review N3): it is logged as `config.setup_token_invalid` and `setup.config_invalid`, setup fails closed while it is needed, and once an administrator exists the variable is ignored. The error never repeats the value). When empty, the server generates 32 random bytes (256 bits, base64url) at startup and prints them once in a console banner while setup is still needed. A startup hook (`apps/web/instrumentation.ts`) waits for the database and migrations, so the stack can start before the migration step, and prints nothing once an administrator exists. If the hook could not run, the first visit to `/setup` prints the banner.
- **Never persisted.** The generated token lives only in process memory (and in the one console banner, which Docker stores in its container log; treat that log as sensitive until setup is complete). It is not stored in PostgreSQL, not in audit rows (`bootstrap.completed` records `method: setup_token` and `tokenSource: env | generated` only), and not in structured logs (the `log()` redactor also masks any `token` field). A configured token is never printed; the banner names the variable. After setup the generated token is dropped, nothing is printed again, and a later start prints nothing.
- **Comparison and limits.** Constant-time comparison (SHA-256 of both sides, then `timingSafeEqual`, via the existing `safeEqual`). Failures are limited in memory to 10 per 15 minutes overall plus 5 per trusted client address (an attacker can use any address, so the global budget is the real limit; per-address applies only through the trusted proxy path). While a budget is spent even the right token is refused (otherwise the limit would not stop guessing), which lets an attacker delay setup but never complete it. Review N2: anyone who can reach the page can keep setup locked by spending the budget every 15 minutes; this is accepted as an availability-only risk and the documented recovery is restarting the web process (which also replaces a generated token) and finishing setup while the page is reachable only privately. A correct token deliberately does not bypass the budget, since that would let an attacker guess past it. The limit check, comparison and failure record are one synchronous step, so concurrent bursts cannot exceed the budget (tested with 60 concurrent guesses). Input errors with the right token do not spend attempts. In-memory counters reset on restart, which is an operator action; the limit assumes one web process, as the supported topology already does (a second process would double the budget and have its own generated token).
- **Closing and races.** The service answers `not_found` before reading the body once an administrator exists, so a completed install exposes nothing (the page is a 404 as well). Two simultaneous valid requests serialize on the existing advisory lock and `bootstrap_state` primary key: one household, the loser gets `bootstrap_closed` (tested with 8 concurrent requests). The household and administrator are created in one transaction with the audit row.
- **Why only the owner of the token can claim it.** An exposed install can be claimed only by someone who knows the token. A generated token is visible only to whoever can read the server console; a configured token only to whoever can read the configuration. Operators must still complete setup before exposing the proxy publicly, or use a tunnel (documented in the operations guide).
- **dev-up launcher.** While no administrator exists (checked with `select count(*) from bootstrap_state` after migration) the launcher generates its own random token, passes it to the web container through the environment of the single `docker compose up` command and prints it on screen once, instead of reading the server's console banner. Nothing is written to `.env`, a log file or a temporary file by the launcher, and the web container then does not print the token. A token the developer defined is used and not displayed; once an administrator exists nothing is shown.
- **Known limitation.** The Windows launcher and the Compose and CI smoke steps changed here were not run without a Docker daemon in the implementation environment (CI covers the Compose smoke steps).

## Password change and administrator reset decisions (owner request, 2026-11-14, phase 1)

The owner asked for administrator-issued temporary passwords with a forced change, and a normal change-password page (this closes the "no password change or reset" gap recorded under the M01 decisions). The self-service "Forgot password" email flow is phase 2 and is not built here.

- **Model.** A reset writes the Argon2id hash of a random temporary password into `users.password_hash` (the old password stops working at once) and sets `users.must_change_password`. `password_resets` (migration 0010) records each credential without any secret: kind (`admin_temporary`, with `email_temporary` reserved), issuer, status (`open`, `used`, `completed`, `superseded`), expiry. One open credential per account is enforced by a partial unique index. Expiry is derived from `expires_at` against the database clock. Starter choice: a temporary password replaces the real one instead of living beside it, so a reset after a suspected compromise really revokes the old password. Consequence for phase 2: an email-initiated reset by itself would let anyone who knows an address lock that person out of their own password. Phase 2 should keep the existing hash valid until the emailed password is used (store the temporary hash on `password_resets` and let sign-in accept either), or require possession of the mailbox before changing anything; that choice is left to phase 2.
- **Temporary password.** 20 symbols from a 31-symbol alphabet without lookalikes (about 99 bits) in four dash-separated groups, from the operating system's CSPRNG with unbiased selection. Shown once to the administrator on a `no-store`, `no-referrer` page or in the JSON response; not stored, logged or audited. Valid 4 hours by default (`TALLYMED_TEMP_PASSWORD_SECONDS`, 5 minutes to 7 days) and single use: the first successful sign-in consumes it under a row lock, so a race produces one session. A correct but used or expired temporary password gets the specific `temporary_password_expired` answer (only someone who holds the secret can see it; wrong passwords and unknown accounts stay indistinguishable) and still counts toward the lockout.
- **Forced change.** Sign-in with a temporary password yields a session of at most 15 minutes (`TALLYMED_PASSWORD_CHANGE_SESSION_SECONDS`). While the flag is set the actor can only post to change-password and sign-out: `route()` refuses everything else with `password_change_required` unless a route opts in (closed by default); page and GET helpers refuse it; the shell layout and every page redirect to `/password/change`, which lives outside the app shell. A test inventories every API route and every catch-all action and fails if a new route is unclassified. If the restricted session lapses before a new password is chosen, the same temporary password can start a new one within its own expiry, but only while no session of the account is live (checked under the user row lock), so a leaked copy cannot join a session in progress; racing retries produce one session.
- **Change.** A normal change requires the current password and is throttled per account (five wrong guesses per 15 minutes, audited once and at lockout). A forced change does not ask again for the temporary password. The new password must pass the policy (12 to 128 characters, unchanged here) and differ from the current one. Every session of the account is revoked and a fresh one is issued to the caller. Sign-in re-reads the user under a row lock before issuing a session, so a password change or reset that commits between verification and session creation cannot be bypassed with the old password.
- **Administrator rules.** Admins cannot reset themselves (they use change password), disabled accounts are not reset, and the reset needs the row version (a double submit or two concurrent resets issue exactly one secret). It runs under the household administrator advisory lock (shared with role and status changes), re-checks inside the lock that the actor's session is live and still an administrator, and refuses unless another active administrator with a usable password remains, so two administrators cannot reset each other into a lockout. Role and status changes use the same rule: the last-administrator check counts only active administrators who are not waiting to change a temporary password, so resetting another administrator and then demoting yourself is refused. A reset also clears the target's sign-in lockout.
- **Audit.** `auth.password_reset_issued` (administrator, target, expiry, sessions revoked), `auth.temporary_password_used`, `auth.password_changed` (forced flag, sessions revoked), bounded `auth.password_change_failed` and `auth.password_change_locked`, and `auth.login_failed` with a reason for an unusable temporary password. No secret appears in any row or log; a test searches every audit, reset, throttle and session row and the log output for the secret.
- **Not done here (phase 2 or later).** Forgot-password button and email delivery (depends on the SMTP settings page built in another thread), common-password checks, MCP credentials are not rotated by a reset (they belong to the household, not the person; the operator guide says to revoke them after resetting a possibly compromised administrator), expired restricted sessions and old reset rows are not pruned, the HTML pages were checked in a browser only where the environment allowed (see the PR).
- **Migration numbering.** This work uses 0009. Another thread adds its own migration; whichever merges second renumbers (`migrations.test.mjs` and `hsa.test.mjs` list the applied versions).

## Administrator settings, email and trusted proxy decisions

- **Editable versus environment.** Editable in the app: corresponding-source link, session length, inactivity limit, invitation lifetime, document size/storage/retention limits, SMTP, and the trusted proxy list. Environment only (shown read-only, secrets as set/not set): canonical origin, database URL, proxy shared secret, secrets key, setup token, document volume path, MCP listener and its role, listener bind and TLS. Built-in limits (sign-in, upload, settings) are displayed, not editable. Precedence for an editable value: stored setting, then environment, then default; a blank field restores the environment value.
- **Storage.** One `server_settings` row per group (migration 0010) with optimistic versioning, applied to the running config in place and re-read at most every five seconds per process (and immediately after a save in the saving process). The cleanup CLI reads the stored retention value. The settings table is server-wide and is not granted to the MCP role.
- **Re-authentication.** Every settings save asks for the administrator's own password, checked on the server, with a per-process lockout after five wrong answers in 15 minutes. The test email needs no password because it can only reach the administrator's own address and is rate limited.
- **Secret key.** New `TALLYMED_SECRETS_KEY` (32 to 64 random bytes, base64, at least 16 distinct byte values; no key is shipped, `dev-up` generates one locally). No earlier decision defined at-rest encryption, so this one is the first; AES-256-GCM with HKDF per setting and the setting name as authenticated data. Without it a relay password cannot be saved; changing it makes the saved password unreadable until it is entered again (reported, not an error). Not rotated automatically.
- **SMTP policy.** Ports limited to 25, 465, 587, 1025, 2465, 2525; credentials only over TLS or STARTTLS (never with "none"); certificates verified, TLS 1.2 minimum; host resolved in the app and the checked address connected; private LAN addresses allowed because home relays are common; loopback and link-local only by explicit setting; metadata, multicast, unspecified and reserved addresses (for IPv6 anything outside global unicast and unique-local, plus Teredo and documentation ranges) never; mixed answers refuse the host. Failures are reported by category without remote server text. nodemailer 7 is the SMTP client (pinned); its types are declared locally to avoid a large optional dev dependency tree.
- **Email helper contract.** `isEmailConfigured` and `sendEmail` in `server/email.ts`; delivery problems are results, not exceptions; no address, body or secret in logs; the caller audits its own action. Process-wide cap of 60 messages per hour.
- **Trusted proxy.** The owner asked for an IP/CIDR list in the admin page. The app cannot read the socket from a route handler, so the server records each request's peer address in `instrumentation.ts`, signed with a per-process key (a missing or invalid signature means "unknown", never trusted). The list (stored or `TALLYMED_TRUSTED_PROXIES`) and the earlier shared secret are alternatives: either one makes a request trusted. Default trusts nothing; ranges shorter than /8 (IPv4) or /32 (IPv6) are refused, and wide or public ranges need an explicit confirmation and show a persistent warning. The client address is the right-most `X-Forwarded-For` entry that is not a listed proxy. Throttle keys still use only trusted addresses (unchanged design): untrusted requests share the `untrusted` bucket and the per-account limit applies. The page shows what the app sees for the current request.
- **Known limits.** Settings and email rate limits are per process. Settings changes in one process reach another within about five seconds. Migration is 0010 (0009 is password reset). Before a forgot-password flow calls `sendEmail` from an anonymous endpoint it needs per-recipient and per-address limits and failure accounting: the process-wide 60 per hour budget could otherwise be exhausted by one client.

## Forgot password by email (owner request 2026-11-14, phase 2)

- **Emailed credential stays beside the password.** Replacing the password on request (as the administrator reset does) would let anyone who knows an address lock that person out. The emailed temporary password is stored hashed in `password_resets.secret_hash` (migration 0011; required for `email_temporary`, forbidden for `admin_temporary`) and takes the password's place only when used to sign in, which then follows the PR #14 forced-change path (restricted session, other sessions revoked). `issueTemporaryCredential` is now administrator-only; the earlier test that issued an `email_temporary` credential through it was removed because that pattern is the unsafe one.
- **Sign-in handling.** Login verifies the typed password against the account hash and, always, against the open emailed hash (a dummy when none, so timing does not reveal a pending reset). A normal sign-in supersedes an unused emailed credential and audits `auth.password_reset_cancelled`. Both verifications share the existing sign-in throttle.
- **No enumeration.** One response for known, unknown, disabled, limited and over-budget-for-this-account requests; identical work; the email is sent after the response. Limits are keyed on the submitted address and the client address (table `password_reset_requests`, SHA-256 digests with their own prefix, so requests never count toward sign-in lockout); limited requests are not recorded so the window cannot be extended. Account limits (one per ten minutes, three per 24 hours) count issued credentials, including failed deliveries; process budget 20 reset emails per hour below the helper's 60 (closes the open item recorded under admin settings).
- **Other choices.** Credentials last at most one hour; the recipient is the stored account address; no link in the email; an admin-issued or already-used credential is never replaced; the page without SMTP explains to ask an administrator and `/api/auth/forgot-password` answers `409 email_not_configured` (reveals only server configuration, which the page shows). Delivery failure retires the credential and is audited by category.
- **Known limits.** Client/process counters for the client address and the process budget are per-process in the helper but the request and account counters live in the database. Users behind one unconfigured proxy share the untrusted budget. A stranger can trigger up to three harmless emails per day to a real person. Not done: pruning of old `password_resets` rows, a per-household switch to disable the feature (turn off by clearing SMTP).
- **Review follow-up (M1, L1 to L3).** M1: a request is refused only while an unexpired administrator-issued or used credential is pending; once it has expired a new emailed credential is issued and can be used even though the account is still flagged, so abandoning a forced change no longer strands the account (for the sole administrator too). L1 accepted and documented: a newer request supersedes an older unused emailed password (one open credential per account); the email says to use the newest message. L2 accepted and documented: availability limits are shared and anonymous by design. L3: client addresses in `password_reset_requests` are digests, and the second password verification at sign-in runs only after the account password failed. Not changed: a failed send still spends a reset-budget token (a few tokens of headroom).
- **Review follow-up N1 (blocking, fixed).** Issuing a recovery credential while the account was still flagged from an abandoned reset left the expired temporary hash in `users.password_hash`, and the new open credential made sign-in treat that stale hash as valid. Now the stale hash is replaced by an unknowable random one in the same transaction that issues the recovery credential, and sign-in additionally refuses the forced-change branch when the pending row is an unused emailed credential (a used one, which owns the stored hash, still works). Regression test: the exact stranger-request sequence.

## Sign-in with an OpenID Connect provider (owner request, 2026-11-14)

- **One protocol, one provider.** Generic OpenID Connect with presets for Google (fixed issuer) and Microsoft Entra ID (issuer built from one directory ID; the shared `common` endpoint is refused because any directory could then vouch for an address). GitHub is left out: it offers OAuth 2.0 without OpenID Connect ID tokens, and a second protocol with its own email-verification rules was not worth the review surface. No OIDC library was added; the protocol code is about 250 lines over `node:crypto` and is covered by a mock-provider test file.
- **Code flow with PKCE, state and nonce, always.** The three values travel in one encrypted, HttpOnly, SameSite=Lax cookie that lives ten minutes and is cleared on every callback. No server-side flow table: an unauthenticated visitor cannot make the server write rows, and the binding to the browser is the cookie itself. The provider's single-use code prevents replay.
- **Linking by verified email, then by subject.** First sign-in links the subject to the account with the same address only when the provider asserts the address is verified (`email_verified` literally true; `xms_edov` for Microsoft's issuer only). Afterwards the subject is the key and address changes at the provider do not matter. A second subject for an already linked account is refused, never swapped in. An administrator can remove a link on the Sign-in page.
- **Never an administrator, and nobody by default.** Auto-provisioning is off unless ticked, requires at least one allowed email domain (otherwise any Google account could join), and always creates a Standard user with a random unknowable password. Roles stay a decision on the Users page; no claim is mapped to a role.
- **Passwords stay unless proven unnecessary.** Turning password sign-in off is accepted only from an administrator who has signed in through the saved provider configuration, and not together with a change of issuer, client or secret. The switch is evaluated on every use, not just when saved: passwords are on again whenever provider sign-in is disabled or unusable or no active administrator is linked, and `TALLYMED_PASSWORD_LOGIN=on` forces them on for a provider outage. Password confirmation for settings is unaffected.
- **Secret and key.** The client secret is the `signin` group's encrypted secret (same mechanism and key as the SMTP password, its own purpose label). Provider sign-in needs `TALLYMED_SECRETS_KEY` even for a public client, because the same key encrypts the flow cookie.
- **Outbound requests.** https only, no redirects, bounded, and connected only to addresses that pass the SMTP relay's address policy at connection time. Private network addresses are allowed because a self-hosted provider on the same network is the main case. `TALLYMED_OIDC_ALLOW_INSECURE_ISSUER=true` (http and loopback) exists for tests and local development and shows a warning on the page.
- **Base address.** The redirect address is `TALLYMED_CANONICAL_ORIGIN` plus a fixed path and is displayed for copying. It does not depend on the trusted-proxy list or on request headers.
- **Known limits.** One provider at a time; no provider logout; no group mapping; the attempt limiter is per process; an account disabled at the provider keeps its TallyMed session until it expires or the account is disabled here; accounts created at first sign-in cannot confirm settings with a password unless an administrator issues one (they are Standard users, so they have no settings to confirm).

## Backup and restore from the app (owner request, 2026-11-14)

- **What existed.** Backup was an operator procedure only (`pg_dump`, a tar of the documents volume, `age`); nothing in the interface. That procedure stays documented and is still the way to take unattended backups.
- **One archive.** Server settings > Backup streams a gzip tar: `data/<table>.<part>.ndjson` (one JSON row per line from `row_to_json`, read in one repeatable-read snapshot), `documents/<object key>`, and `manifest.json` last with the format version, application and schema version, per-table row counts and SHA-256 digests, per-document sizes and digests, and the ledger totals. Standard `tar` can list it. With a passphrase (12 characters or more) the whole stream is encrypted: scrypt, then AES-256-GCM in 64 KiB frames with a counter nonce and a final-frame flag, so truncation and reordering are detected.
- **What is never in it.** Sessions, invitations, password-reset rows and request counters, sign-in attempts, the SMTP password and email settings, the trusted-proxy list, the setup token, `TALLYMED_SECRETS_KEY`. Assistant client tokens are replaced by an unusable digest, so every assistant client must be issued a new token after a restore. Password hashes are included (a restore without accounts is not usable), which is why the page recommends the passphrase. Every table is listed as included or excluded in `tables.ts`; a test fails when a migration adds a table that is in neither list.
- **Who and how.** Administrators only (`settings:manage`), current password again, one backup at a time per process, audit entries `backup.started`, `backup.completed`, `backup.failed` (with a reason category, never content).
- **Restore only into an empty installation.** There is no restore into a running household: merging two ledgers cannot be made safe, and overwriting is a destructive action the interface should not offer. The web path is `/setup/restore`, available only before the first administrator exists and guarded by the setup token and the bootstrap advisory lock; the CLI does the same and can also bring an empty database to the backup's schema version and then upgrade it. The web path requires the same schema version.
- **Verification before commit.** The restore runs in one transaction. Rows are loaded with the tables' own triggers disabled (as `pg_restore` does), because insert-time guards look at the present state of related rows and would refuse valid history; checks, foreign keys and unique indexes stay on. Then every table is exported again and its digest must equal the manifest, the money rules the deferred guards enforce are re-checked over the whole database (`ledger.ts`), the ledger totals must equal the manifest, and every document must match `document_versions`. Any difference rolls everything back and removes the files the restore wrote. `backup.restored` is audited.
- **Archive parsing.** Own strict tar reader: only regular files, only the three name patterns (no directories, links, `..` or absolute names), sizes from the header checked against a cap, manifest capped, total upload capped by `TALLYMED_RESTORE_MAX_MB` (default 4096) both compressed and decompressed, document keys must be 32 hex characters and present in the manifest.
- **Known limits.** No scheduled backups, no restore into a non-empty installation, no partial restore. The upload is spooled to disk (needs free space of about the archive size). A reverse proxy's own upload limit applies first. The single-flight guard is per process.

## Saved payment methods and "paid with" (owner request, 2026-11-15)

- **Request.** Record which specific card or account paid a payment, with named payment methods that can be tracked. It sits beside the existing payment type (card, bank transfer, check, cash, portal, other), which is unchanged; the form now labels that dropdown "Payment type" so the two are not confused.
- **What is stored.** `payment_methods` (migration 0015): a nickname (1 to 60 characters, unique among active methods ignoring case), a type (credit card, debit card, HSA/FSA card, bank account, other), optionally the last four digits, and an archived flag. Nothing that could charge anything is accepted: no full number, expiry date or security code. Unknown fields and anything but exactly four digits are refused, so a pasted card number cannot be stored in the last-four field, and a nickname with nine or more digits in a row (spaces and hyphens ignored) is refused by validation and by a table check. A form shows the generic conflict banner for a duplicate nickname; the specific message reaches JSON callers. Methods are never deleted (a trigger refuses it); archiving hides one from new payments and keeps every existing link.
- **Why a separate history table.** A payment header is immutable (`ledger_immutable`). `payment_method_assignments` is an append-only history of "paid with" choices (a null method clears it); the newest row per payment is current. This lets an existing payment, which starts with no method, be assigned later without loosening the payment trigger, keeps every change audited, and cannot affect an amount, an allocation or a balance. Choosing the current value again writes nothing. A voided payment cannot be changed.
- **Races.** An assignment names a method that is active at that moment: a database trigger takes a share lock on the method row and refuses an archived one, and the archive action takes the row lock, so recording and archiving serialize. Lock order is payments, bills, plans, then the payment method last; archive holds no payment lock, so no cycle exists. Tested with concurrent archive against record and `retryStats.lockConflicts` at 0.
- **Totals.** The Payment methods page shows, per method, the number of payments and net cash using the cash summary's definition (refunds subtracted, voided counts zero), plus the payments with no method recorded; the figures add up to the cash summary. A total is by current method, so changing a payment's method moves its cash between methods.
- **Audit and backup.** Audit rows carry ids and flags only (`paymentMethodId`, `fromPaymentMethodId`, `toPaymentMethodId`, `renamed`), never a nickname or digits. Both tables are in backups (`since: '0015'`) and restore under the existing trigger-off load. The assistant database role has no grant on either table.
- **Starter choices the owner can revisit.** Any user who can write expenses can add, rename and archive methods (no admin-only gate); nickname changes show on old payments because payments show the current nickname; the type list is fixed; no per-method statement import, balance or limit tracking; HSA reimbursement flows are not changed (an HSA/FSA card is only a label).

## HSA accounts and direct HSA card payments (owner request, 2026-11-15)

- **Request.** Create an HSA account, link an HSA card to it, and pay directly with that card, bypassing claim submission. TallyMed is a ledger and never moves money, so "pay with HSA" means recording that a payment was paid straight from the HSA at the point of service. No payment processor, card network or tokenization is involved: only a name, an administrator and the last four digits are stored, so the app stays outside PCI scope. A name or administrator with nine or more digits in a row (spaces, hyphens, dots, slashes and underscores ignored) is refused by validation and a table check; this is a best-effort label guard, and a number split by some other separator would pass.
- **Data (migration 0016).** `hsa_accounts` (name, administrator, last four, archived; never deleted); `payment_method_hsa_links` (which account a saved payment method draws from; changeable); `payment_hsa_funding` (append-only: this payment was paid directly from that account). The link is its own table rather than a column on `payment_methods`, so a backup from before 0016 restores cleanly.
- **Direct means settled.** A payment is direct only when it is recorded with a card linked to an HSA account; the funding row is written in the same transaction and never afterwards. If it cannot be written (archived account, lost race) the whole payment fails; it never falls back to an ordinary, claimable payment. Cards with no link stay labels, and their payments stay claimable.
- **The one change to existing HSA arithmetic.** `hsa_allocation_status.available_cents` is zero for a directly paid payment, and the view gains a `direct_hsa` column at the end; no other column changed position or meaning (a test runs the original 0006 definition against the same data and compares every ordinary row). Claims and external reimbursements therefore refuse on available, with an explicit message. Direct allocations take no eligibility decision (it would have no effect), so they leave the "not decided yet" count and queue. The HSA page shows "Paid directly from HSA" beside the claim figures, counting cash applied to bills (the accounts table on the HSA page counts whole payments, applied or not, and ignores the page filters, so the two differ by unapplied direct cash and by the filters); the allocation pill reads "Paid from HSA" and the CSV export marks the decision `paid_directly_from_hsa`; eligible still equals pending + received + available for claimable payments.
- **Enforced in the database, both ways.** No HSA entry or eligibility decision on a direct payment, and no funding on a payment that already has HSA entries or decisions. Both are commit-time guards that take the payment row lock first (like the other HSA guards), so they are race-safe against each other; the backup ledger checks mirror the rule (only where the table exists) because restore loads with triggers off.
- **Paid with and direct agree when written.** (Relinking a card later does not rewrite a payment already recorded; the payment page always keeps the payment's current card selectable, and choosing it again changes nothing.) An HSA-linked card can be chosen only when a payment is recorded. On an ordinary payment it is refused (that would claim the HSA paid without being so); a direct payment can change only to another card of the same account and cannot be cleared. Refunds and voids on a direct payment work as for any payment (cash returns to the HSA).
- **Lock order.** Payments, bills, plans, payment method, then HSA account last. Archiving an account blocks new direct payments with its cards and keeps old links; tested against recording with `lockConflicts` at 0.
- **Starter choices the owner can revisit.** Existing payments cannot be marked direct afterwards (the funding is written when the payment is recorded); an HSA/FSA card is only a direct payment once linked; one account per card; any user who can write expenses can manage accounts; no balances, contributions or limits per account; direct payments are not auto-checked against HSA eligibility rules (that stays the household's judgment, and TallyMed does not give tax advice).


## Admin delete, payment method change and undo decisions (owner request, 2026-11-15)

- **Delete is a hidden, audited removal; no row is ever deleted.** A payment is removed by reversing every allocation with linked entries and appending a `remove` event (`payment_removal_events`); a removed payment keeps no applied or refunded cash, so every cash figure, allocation view and HSA view already shows zero and only lists, pickers and counts filter it. A plan is hidden with `removed_at/by/reason`, its live matches are released with negative match rows, and no payment or bill is touched. Restore appends a `restore` event and re-posts the allocations as NEW entries through the normal bill-room guards.
- **Supersedes earlier choices.** "There is no delete path" and "plan cancel is final" no longer describe the product: an administrator can delete a payment or plan, and undo it for a short time. Cancel itself stays final.
- **Owner-visible starter choices.** (1) Only administrators delete, undo or release an HSA funding (`records:remove`). (2) A payment with refunded cash still out, or with any HSA decision, claim or reimbursement, cannot be removed; the message says what to do first. A refund that was reversed again no longer blocks. (3) Undo restores cash allocations but does not re-create plan matches of a removed payment; undo of a plan removal re-posts a match only if it still fits and lists the skipped ones in the audit. (4) One undo slot per user, three minutes by the database clock, replaced by the user's next mutation through the shared pipeline (a failed attempt or a replayed submit also supersedes it). Only removals and method changes set it. (5) Releasing a direct HSA funding (moving the payment to a card with no HSA link, or clearing it) is append-only (`payment_hsa_funding_events`), makes the payment ordinary and claimable, and can be undone; moving an ordinary payment onto an HSA card, or a funded one to another account's card, stays refused. (6) Undo of a release is refused if the HSA account was archived in the meantime.
- **Removed records and what they hold (migration 0018).** (1) A removed or voided payment takes no new HSA exposure: an eligibility decision, a claim reservation or an external reimbursement is refused by the service (a conflict that says the payment was removed or voided) and, at commit, by the database (`hsa_refuse_removed_payment`, a deferred constraint trigger on `hsa_eligibility_decisions` and `hsa_entries` that takes the payment row lock first, like the direct-HSA guard). Settling what already exists (a receipt, rejection, cancellation or receipt reversal on an earlier claim) is not new exposure and stays possible, so a voided payment that carried a claim before this fix can still be settled; reads are unaffected, and undo of a removal reopens the payment for decisions. A backup restore loads rows with the tables' own triggers off, exactly as for the other HSA guards, so a decision on a voided payment written before this fix restores (tested); the ledger rules do not forbid it. (2) Matches of a removed plan count as nothing: `allocation_match_check`, `matchedCents` on an allocation, the unmatched-cash pickers, the plan locks taken before a refund or removal, and the backup ledger rule all skip plans with `removed_at` set. The match rows stay as history. Cash of a removed cancelled plan can therefore be matched to a new plan (up to its net cash), and the old plan stays hidden everywhere; unmatching on a removed plan stays refused because the plan is invisible. The backup summary's `matchedCents` total still counts every current-schedule match, removed or not, so a backup made before this change still verifies. (3) Undo of a plan removal shows the plan again, which counts its matches again: an active plan re-posts the released matches that still fit (unchanged); a cancelled plan keeps its history, so undo releases, with appended unmatch rows and latest due date first, whatever an allocation no longer holds beyond its other matches, and lists those matches with the skipped ones in the audit (`plan.restored`). A deferred guard on restoring a plan (`payment_plans_restore_guard`) re-checks every allocation the plan matched, so a restore can never leave cash matched above its net.
- **What the read paths show (HSA and other screens).** The HSA side lists, counts, totals, queues and exports an allocation only when its payment is not removed and it is not a fully reversed allocation (net cash zero) with no HSA history (no eligibility decision and no HSA entry). One SQL predicate, `HSA_VISIBLE_ALLOCATION` in `repositories/hsa.ts`, serves the list, the totals, the queues and the allocation export, so they always agree; no migration. So a removed payment has no HSA row or count, and after an undo the restored allocation is the only row (the original, fully reversed one is not listed beside it). A zero-net allocation that has a decision, a claim or a receipt stays visible (history and needs-review cases). The HSA allocation page answers not found for a removed payment. The events and decisions exports need no filter: a payment with any HSA entry or decision cannot be removed, and a removed payment takes no new ones. The HSA accounts table counts only payments that are not voided (a voided payment holds no cash), like the cash figures beside it. Intentionally unfiltered: the bill ledger and payment detail show the real entries of a live payment (including reversals and re-posts after an undo), and the plan match history keeps its match and release lines.
- **Known gaps carried (owner-visible).** The free-text reason is kept on the event row, not in the audit detail. Server refusals reach the page as an error code, not the exact sentence. The delete dialogs need JavaScript. Browser coverage does not include plan deletion or the HSA release flow (server tests do).

## Add a plan that is already in progress (owner request, 2026-11)

- **Request.** Entering a plan that started months ago and was restructured took several steps (create with the original terms, match past payments, revise with "keep paid"). One guided form now does it in one save: "Add a plan already in progress" beside "Create plan" on the Payment plans page. - **One transaction, one key, the same writes.** The service refactors `createPlan` and `revisePlan` into shared tx-level functions (`lockCreateScope`, `writeNewPlan`, `writeRevision`) that both the old and the new service call, so a plan entered in one step is recorded exactly like one entered in several. `createPlan` and `revisePlan` keep their fingerprints, locks, refusals and audit detail unchanged (all earlier plan tests pass without edits). - **Reason is required only with "Yes".** With "No" there is no revision to describe, so the field and the restart fields are ignored rather than refused (a form without JavaScript always sends them).

The "Day of month" field applies a typed value only when it is whole (two digits 10 to 31, or one digit 4 to 9), or on Enter or blur, so typing "1" on the way to "15" no longer rewrites the date; Enter in that field no longer submits the surrounding form.
- **Not done / left for the owner.** No "list each remaining installment" for the restructure (per-installment only, as asked). The restart cadence offers weekly, biweekly and monthly. A second dialog on the Payment plans page means browser checks address the open dialog (`dialog.form-modal[open]`).

The lifecycle states are `pending`, `approved`, `rejected`, `expired`, `superseded`; the last two are reserved and nothing sets them yet (no expiry job was asked for; a stale proposal is shown as such and can be rejected).
- **One strict payload schema for both sides.** `server/plan-proposal.ts` (zod and money only) is imported by the listener's service and by the web app, so the tool refuses what the app would refuse and the app validates the stored JSON again before it shows or applies it. It uses the app's limits (120 installments, 20 bills, `MAX_CENTS`, dates 1900 to 2100, USD strings that parse to whole cents). Amounts are canonicalized to plain decimal strings on the way in. The import allow-list test for the MCP side was widened by exactly three modules for this: `plan-proposal.ts`, `untrusted-text.ts` (the text cleaning that moved out of `services/mcp.ts`) and `money.ts`; none can write.
- **What the MCP role can and cannot do.** It can insert a pending `plan_proposals` row (column-level insert on `id, household_id, client_id, payload, bill_versions, note`, so it cannot set a status, decision, plan id, version or time) and read back `id, household_id, client_id, status, decided_at, created_at` (for the caps and its own list). It cannot read the payload, note, decision or created plan, and has no right at all on `payment_plans`, `plan_revisions`, `plan_installments`, `installment_matches`, `payment_plan_bills`, payments or HSA tables; the startup check verifies insert privileges per column. One new audit action and entity type are allowed to it (`plan_proposal.created`, `plan_proposal`); the approve and reject actions are not. To check bills it reads only the bill columns it already had (household, id, amount status, version); whether a bill still owes money is a person's review, rechecked in the app.
- **Approval is `saveInProgress` with two hooks, not a copy.** `createPlanInProgress` keeps its parse, fingerprint and idempotency claim; everything after the claim became `saveInProgress`, which the approval calls inside its own transaction under its own single key (`proposal.plan_approve`). `locked` (after payments and bills are locked) and `gate` (after the composition) run before the first write, so every refusal writes nothing. The plan the approval writes is therefore the plan the form writes, with the same events; only the summary event gains `fromAssistantProposal` and `assistantProposalId`, and only for an approval. The restructure's revision reason is a fixed server sentence, not the assistant's text.
- **Lock order.** Payments (those on the bills, when matching), then bills in id order, then plans (new row, never waited for), then the proposal row. This follows the document approval, which also locks its proposal last. It is safe because the only other proposal-row locker is a rejection, which holds nothing else, and the listener never locks.
- **The preview is the commitment.** The approval form carries the SHA-256 of the preview the person saw (`previewDigest`); under the locks the approval recomposes the preview from the cash as it then is, and refuses with `stale_version` if it differs (a payment arrived, a bill was edited, the date moved). This is the plan-proposal counterpart of the document proposal's pinned versions: "approve creates exactly the plan the preview shows". A bill edited since the proposal (its `version` differs), no longer confirmed, or owing nothing also refuses. A proposal from a revoked credential can only be rejected, as for documents.
- **Caps count both kinds.** The pending caps (50 per credential, 200 per household) count document and plan proposals together under the existing household advisory lock. There is no one-per-plan uniqueness: duplicates are bounded by the caps.
- **Untrusted text.** The plan name and the note are cleaned (control, bidirectional and zero-width characters) and length-capped; both are displayed as plain text only, and the name becomes the plan's name only when a person approves. Neither is in any audit row or log.
- **Backup.** `plan_proposals` is a backup table (since 0019), like the document proposals; the assistant credentials it points to are restored with unusable digests.
- **Not done.** "Open in the form to edit" (pre-filling the in-progress dialog from a proposal) is not built: the one mapping, `planProposalFormInput`, exists for it. No expiry of old proposals. The `list_my_plan_proposals` tool shows status only. The browser check covers one proposal (a generated schedule without a restructure); the restructure path is covered by the service tests.

## Admin delete for HSA decisions, claims and reimbursements (owner request, 2026-11-16)

- **Request.** After a payment recorded with an HSA card by mistake was deleted, its HSA record stayed on the HSA page. The hiding of removed payments and their zero-net leftovers on every HSA view is the read-path fix in #41. The owner then asked for an administrator Delete for HSA claims, decisions and reimbursements, with undo, because nothing retroactively fixes older HSA records.
- **Why markers.** A receipt reversal lowers `received` but does not return a claim line to pending, and a receipt can be reversed once, so compensating entries can never be undone exactly. Delete is therefore an append-only removal marker (`hsa_removal_events`, migration 0020) and a removed record is not live. Nothing is physically deleted. `hsa_live_decisions` and `hsa_live_entries` are the one definition of live; the HSA guards, the `hsa_allocation_status` view, the funding checks, `removalBlockers` and every reader use them.
- **Starter choices the owner can revisit.** (1) Deletes are leaf-first: reimbursements, then the claim, then a decision that supports them; the page shows the reason beside a disabled button instead of failing. (2) A removal is allowed whenever it does not make an allocation's needs-review excess larger, so stale records on an allocation already in needs-review can be cleared; a restore is strict and refused if pending plus received would exceed the eligible ceiling. (3) Undo uses the same one slot per user and three minutes as the payment and plan deletes; it is refused if the world changed (the payment was removed, voided or paid directly from an HSA meanwhile, a deleted claim's reference was reused, the ceiling no longer allows it). (4) Claim references are unique among live claims only, so a deleted claim's reference can be entered again. (5) Documents attached to a removed decision or receipt stay attached and show as deleted without a link; nothing new can be attached to them. (6) Administrators only. (7) After the HSA records of a payment are deleted, the payment itself can be deleted.
- **Known gaps (owner-visible).** The refusal sentences of a failed undo and some leaf-first messages are new wording. Another administrator's later remove or restore of the same record is detected only by the record's current state, not by event id. The deletable check in the services mirrors the database guard in TypeScript and is advisory; the guard is authoritative. The Documents rendering has no browser assertion.

## Keep me signed in, screen lock and security PIN decisions (owner request, 2026-11-16)

- **Request.** A "keep me signed in" option on the login page; a UI lock that locks the interface when the person steps away without signing them out, unlocked by a six-digit PIN; the PIN set during account setup and changeable from the user menu; the PIN hashed, never stored in clear.
- **The lock is server state, not an overlay (migration 0021).** `sessions.locked_at` holds it, so a reload, a second tab, devtools or a browser reopened days later cannot bypass it. It copies the `mustChangePassword` gate: `authenticate` computes `Actor.locked`, `route()` refuses a locked actor unless the route sets `allowLocked` (lock, unlock, logout only), `pageActor` and `requireSession` refuse it, and `/locked` renders no data. The browser only decides *when* to lock (idle timer shared across tabs through localStorage, plus Lock now) and posts a heartbeat while the person is active, because reading a page makes no request. The cover shown while the lock request is in flight stays, retrying, if the request fails.
- **Idle rule on the server too.** An account with a PIN is locked when `last_seen_at` is older than `TALLYMED_LOCK_IDLE_SECONDS` (default 300, minimum 180 so a 30 s heartbeat and the 60 s touch interval cannot lock an active person). It is evaluated before the activity touch (the touch would erase it) and stored. A locked session is not touched. An account with no PIN, or one waiting to replace a temporary password, never locks.
- **Wrong-PIN limit (blocking decision, owner-visible).** Six digits are a million values, so only an attempt limit protects them. The counter is on the **session** (`pin_failures`), incremented atomically before verification, five attempts, and the fifth wrong one revokes the session and clears the cookie. Chosen over a per-account counter so a stranger cannot lock someone else's account and a stolen cookie gets five guesses in total. This is the only case in which the lock signs anyone out. A concurrent burst test shows at most four guesses are ever answered as wrong.
- **PIN storage.** Argon2id (same library defaults as passwords) in `users.pin_hash`, separate `hashPin`/`verifyPin` (the password policy requires 12 characters). Offline guessing from a leaked hash is possible; the PIN is a convenience lock, not a second factor, and the session cookie and password remain the real controls. `pin_hash` is in backups with the other account hashes; sessions are not, so a restored server signs everyone in again.
- **Changing the PIN.** The first PIN needs only the session (nothing to protect yet); changing it needs the current PIN or the account password (never both), so a person at an unattended unlocked screen cannot replace it and a forgotten PIN is recoverable after a fresh sign-in. PIN changes do not bump `users.version` (an administrator's open Users form must not go stale) and do not sign other sessions out.
- **Keep me signed in.** Stored on the session (`remember`), a 30-day absolute and 14-day idle limit from new environment settings, carried across a password change, never applied to the restricted temporary-password session. An unticked sign-in is byte-for-byte the old behaviour (same lifetime, same idle limit; `findActiveSession` only chooses a different idle limit for remembered sessions). Provider (OIDC) sign-ins are not remembered (the checkbox sits on the password form).
- **New accounts.** The PIN is required on the setup and invitation forms (HTML `required`) but optional at the API, so existing scripts and tests keep working; an account without a PIN shows a prompt in the sidebar and never locks. Setup and invitation pass the hash through the existing transactions; no PIN goes into a flash cookie, URL, log or audit row.
- **Starter choices the owner can revisit.** Limits are environment values, not yet on the Server settings page; the lock idle time is global, not per person; five attempts; a server-detected lock (browser reopened at a bare address) returns to the overview after unlocking, while Lock now and the idle timer return to the page; an identity-provider-only account that forgets its PIN needs an administrator's temporary password first; the data of the page is removed from the DOM only when the lock navigation completes.
- **Provider sign-in is not gated by the PIN (accepted limit, owner-visible).** A live identity-provider session in the browser lets someone at a locked screen sign in through the provider without the PIN (the provider proves identity there). Making provider sessions start locked would trap an account that has no password and forgot its PIN in a loop, so it is documented instead. Password sign-in needs the password and is unaffected.
- **Server idle slack.** The server's idle lock waits `TALLYMED_LOCK_IDLE_SECONDS` + 60 s because activity reaches it at most every 30 s (heartbeat, which always touches the session); the browser timer is the precise one and the server rule is the backstop for a closed browser.
- **Review follow-ups closed (PR after #44).** Simple PINs are refused when chosen (repeats, runs, repeated pairs and triples; `weak_pin`). Any temporary-password reset, administrator-issued or emailed, clears the PIN (starter choice: recovery from a possibly stolen session outweighs the inconvenience of choosing a new one). `TALLYMED_REMEMBER_SESSION_ABSOLUTE_SECONDS=0` turns Keep me signed in off (starter choice: an environment switch, not a Server settings field), and the General settings page says kept sessions follow the environment limits. A form post refused because the session is locked returns to the page it came from (Referer, same origin, plain application paths only). Page-level lock gates now have a server-side test (`tests/web/lock-page-gates.test.mjs`, which reads the page sources and fails if a page stops calling `requireSession` or either redirect is removed).
- **Known gaps.** No forced PIN for existing accounts (prompt only); no admin "clear PIN"; the heartbeat and idle timer depend on JavaScript (the server-side idle rule still locks without it); no real screen reader or phone pass.
